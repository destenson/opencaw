## Observations (priority order)

### 1. Session log truncated after turn 1 — B2 still broken (critical)

The session file records only 1 turn. The second query was processed (prompt-turn-6 and prompt-turn-7 exist) but was never written to the session log. The per-turn flush fix from QA 0003 was supposed to prevent this, but here the session aborted before writing turn 2. The likely trigger is the degenerate-response detection in turn 7 raising an error and exiting the session write path before `write_turn` is called for that turn. B2's root cause may therefore be the degenerate-output handler, not the flush path. Fix: `write_turn` should be called with whatever response text was received before raising/propagating the degenerate error.

### 2. Degenerate detection fires on empty `<think>` + valid answer (high)

Turn 7 produced: `<think>\n\n</think>\n\nYes, the context is helpful, but it is also quite cluttered and noisy. From the perspective of an LLM...`

The actual answer is valid. The empty `<think></think>` block caused degenerate detection to fire. B13 fixed trailing `<|im_end|>` tokens, and B12 fixed `<think>…</think>` stored as the answer, but neither addresses the case where the model generates an empty think-block immediately followed by a valid answer. `split_thinking` should treat an empty `<think></think>` (think block with only whitespace content) as a no-op and return the text after `</think>` as the answer without flagging it as degenerate.

### 3. Empty response in search-candidates pass — "visible response" instruction ineffective (high)

Turn 2 presented only search-candidates metadata (no loaded fragments) and the model produced an empty response despite the system prompt saying "A blank or empty response is never acceptable." This is the search-candidates intermediate step, not the final answer step — the model sees only "these files match but haven't been loaded, treat as discovery metadata" and correctly recognizes there's nothing to say, but ignores the visibility instruction. Two options: (a) make the search-candidates presentation explicitly say "describe what you would want to see from these files and why" to force a visible output, or (b) don't show search-candidates to the model at all in the pass that produces the final answer — use it only for retrieval signal, not as a user-visible prompt.

### 4. Multi-pass loaded 37 low-value fragments for a simple overview query (medium)

By turn 5 (the third answer pass for "what is opencaw?"), 37 fragments were loaded including:
- `examples/groq_demo.rs` chunk 3 — single line: `thresholds: RecallThresholds::default_hysteresis()`
- `examples/ollama_demo.rs` chunk 3 — single line: `println!("Ingesting project docs...")`
- `Cargo.toml` chunk 3 — `edition.workspace = true`
- `crates/caw-bench/src/bin/coop.rs` chunk 11 — `.to_string()`
- `crates/caw-index/src/embeddings/onnx_provider.rs` chunk 8 — `let idx = SEQ_HIST_BUCKETS`

These are mid-file code chunks that escaped the `token_estimate < 10` filter because they have 24–34 tokens, but contain zero semantic value — they're arbitrary lines extracted from inside function bodies. The model's answer was identical between 32 and 37 fragments (no signal added). The token floor needs to be raised, or stubs whose summary is a bare code line (no struct/fn/type name) should be filtered at index-build time. A minimum-useful-summary check would catch these: if the stub's summary contains no identifier and is just a code fragment starting with a keyword or punctuation, drop it.

### 5. Documentation loaded in stub-outline mode only, not full content (medium)

README.md chunk 1 was retrieved and injected as `Outline: OpenCAW - Context as Workspace, Architecture, Crates, Anthropic, Groq, ClaudeCode` — section titles only, not the explanatory text. The model synthesized a reasonable answer from code structure, but the README introduction that explains *why* to use opencaw was never in the context. For `wants_explanation=true` queries, documentation stubs (`.md` files) should be upgraded from stub-range to full-content range on first recall. The existing 1.5× score multiplier for `.md` files gets them retrieved, but they're still injected as outlines. The upgrade to full content (the "progressive disclosure" TODO item) matters most here.

### 6. Session history fragment contains only prior user query, not the prior answer (medium)

Turn 7 (second query: "is it helpful?") shows:
`[Session turn 1 — .caw/session-20260508-084805.md] User: what is opencaw and why should I use it?`

The model's answer to turn 1 is absent from the session history fragment. When the model is asked "is the context helpful?", it needs to know what it previously said to evaluate whether its answer was well-supported. The session history should include both sides of each turn: user query + assistant answer (compressed per the B7 fix). Including only the user side makes session continuity incomplete for meta-queries like this one.

### 7. Second query misclassified, wrong retrieval strategy triggered (medium)

"You're using it right now; is it helpful? Is it too cluttered?" was classified as `wants_explanation=true`. The retrieved context (BM25 constants, FlatVectorIndex, IntentFieldScore, GreedyBudgetScheduler) is correct for a generic opencaw explanation but wrong for a context-quality feedback question. The model needed to introspect on the fragments it was already seeing — not receive more code stubs. A "wants_feedback" or "wants_meta" intent category would allow the orchestrator to skip new retrieval and instead summarize the current workspace contents as context. Alternatively, detecting that the query references "the context you see" or "right now" should suppress additional retrieval.

### 8. Consolidation notes are mechanical eviction records with no synthesis (low)

All 14 consolidation notes follow the form "Evicted (relevance decayed to 0.4X)" with a 120-character content excerpt. This tells the model a fragment was evicted with a given score, but adds nothing about what was learned from the content or why it was relevant. Notes would be more useful if they indicated the query context at eviction time ("evicted while answering 'what is opencaw?'") so the model can distinguish "evicted as irrelevant" from "evicted as already answered." The LLM-consolidation path would address this but is disabled; at minimum the mechanical path could record the query that triggered eviction.

### 9. Classifier JSON format not compact (low)

Turn 6's classifier returned a multi-line JSON object. The system prompt says "Return exactly one JSON object — no prose, no markdown fences, no explanation" but doesn't say "on one line." For Qwen3 this is fine; the parser handles multi-line JSON. No action needed unless a strict line-parser is introduced. Noting for completeness.

## Summary

This session reveals two active regressions: session-log truncation (B2) is still broken and traces to the degenerate-response error path, and degenerate detection is firing on valid Qwen3 output with empty think-blocks. The empty-response in search-candidates mode also shows the "always produce visible output" instruction isn't robust to the model's reasoning about insufficient evidence. The retrieval quality for the first query is mediocre — correct at a high level, but polluted by single-line code fragments and serving documentation in outline-only mode. The second query reveals a gap in the intent classifier: meta/feedback queries about context quality have no appropriate slot and get the wrong retrieval strategy.
