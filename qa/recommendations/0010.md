# QA Loop 0010 — Recommendations

Sessions analyzed: `session-20260508-071921.md` (2 turns, 13 prompt files), `session-20260508-072123.md` (3 turns, 18 prompt files), `session-20260508-072432.md` (2 turns visible, 17 prompt files). Model: `Qwen3.6-35B-A3B-UD-Q2_K_XL`. All three sessions ran within 13 minutes of each other and covered nearly identical questions ("what is opencaw?", "what can you do with opencaw?", "is development completed?").

---

## 1. B7 (prior-session flooding) remains critical and is now measurable: 80% of initial context is prior-session history (critical)

Session 072432's first real retrieval call (turn 2, after the intent classifier) contains 7 session history fragments totaling ~2713 tokens out of 3375 total workspace tokens. That is 80% of the available context consumed by prior-session model responses before a single workspace stub is loaded. The 8th fragment is a 662-token search-candidates list — the only real workspace signal in the first retrieval pass.

The 7 history fragments contain the full model responses from sessions 071921 and 072123, which ran on the same questions 3–10 minutes earlier. Because those responses use the same vocabulary as the current query ("context," "recall," "orchestrator," "OpenCAW"), they rank at or above workspace stubs in the retrieval pool.

Consequence: the model's turn-1 answer in session 072432 is nearly identical in structure and content to session 072123's answers, because the prior session's output is the dominant retrieved content. This is self-reinforcing: accurate-or-not, each session's answer is primarily derived from the prior session's answer, not from the workspace.

The in-memory-only fix for B3 is in place (prior sessions don't persist to SQLite), but the in-memory HNSW index still embeds and indexes the full prior-session response text. The fix recommended in 0009 (summarize prior-session history before indexing) has not been implemented.

**Recommendation:** Before indexing a prior session's content into the in-memory retrieval pool, replace each model response with a compact synthesis (1-3 sentences: what was asked, what the main finding was, any specific facts cited). Target ≤50 tokens per prior turn rather than the current 300–470 tokens. This reduces the B7 footprint from ~2700 tokens to ~150 tokens while preserving continuity signal.

## 2. Iterative retrieval hits the token budget ceiling in 3 passes with diminishing returns (high)

For session 072432 user turn 1 ("what can you do with opencaw?"), workspace tokens grow across iterations: 3375 → 5406 → 10149 → 9270. By iteration 3, the workspace is at the budget ceiling (10149 tokens across 47 fragments). The scheduler then evicts down to 9270. Iterations 3 and 4 add progressively fewer unique fragments while the total fragment count grows, indicating the loop is re-retrieving variations of already-loaded stubs rather than finding genuinely new information.

Session 072123 shows the same pattern for the same query: 3235 → 6269 → 6893 tokens across iterations 2–5, with 45 → 48 fragments (+3 new fragments for +624 tokens in the last pass).

The iterative loop is not converging. It continues loading fragments until the budget is exhausted, which takes 3–5 iterations. The per-iteration marginal value drops sharply after iteration 2 but the loop runs anyway.

**Recommendation:** Add convergence detection: if an iteration loaded 0 new unique stubs (after deduplication by stub ID), stop. If the workspace token count grew by less than N tokens in an iteration (suggested N=200), stop. Log the iteration count at which convergence was detected so the QA loop can measure it.

---

## 3. Session history is fragmented into competing chunks that consume retrieval slots (high)

The session history is being chunked at ~400-500 token boundaries and injected as multiple separate fragments, each competing for a retrieval slot. By session 072432 turn 5, there are 7 distinct "session history" fragments in the prompt. Each occupies a retrieval slot that could hold a workspace stub. The fragments often overlap in content: the same assistant response is split across fragment N (first half) and fragment N+1 (second half), so loading both duplicates coverage.

This is distinct from B7 (prior-session history): even within a single session, the current session's own history is being chunked into fragments that compete for workspace budget. In a 3-turn session, by turn 3 the session history alone can occupy 4–5 fragments (~1800 tokens) even if no prior-session content exists.

**Recommendation:** Session history should not compete with workspace stubs for retrieval slots. Inject session history as a fixed, non-retrieval header fragment that is included unconditionally but does not consume the workspace retrieval budget. Cap its size to 1–2 summary fragments regardless of session length. Workspace retrieval slots should be reserved exclusively for stub content.

## 4. Inventory query failure (B4 / 0009-obs-3) still not fixed: TODO.md chunk retrieval remains inadequate (high)

Session 072123 turn 3 ("how many todos are left?") retrieved a TODO.md stub chunk that contained only the structural outline, not the actual TODO items. The model correctly acknowledged it couldn't give a count. The `is_inventory_request=true` classification is set correctly by the intent classifier but has no effect on retrieval strategy — the system retrieves the same way regardless of whether the query is an inventory request or an explanation request.

The TODO.md has 19 chunks. For a count query, the model needs either the full document or a canonical overview stub. Neither is available. This is the same failure documented in 0009 recommendation 3; it has not been addressed.

**Recommendation:** Implement the document-level overview stub for TODO.md, BUGS.md, and SCOPE.md (already in the TODO list as an open item). When `is_inventory_request=true`, boost these overview stubs to the top of the retrieval ranking. The overview stub should contain section headings and completion state (e.g., "Section: Retrieval — 8 complete, 2 open") so inventory queries can be answered without loading all chunks.

## 5. All 203 consolidation notes are mechanical eviction records; zero synthesis notes exist (medium)

The index.db contains 203 consolidation notes, all of the form: "Evicted (relevance decayed to X.XX) during query about '...'." There are no synthesized cross-stub notes of the form "stub A is the implementation of the concept described in stub B" or "stubs X and Y are frequently co-retrieved for queries about Z." The `LlmConsolidation` path (which would generate synthesis notes) was not activated in any session.

The eviction-only notes add overhead to the fragment headers without providing model-useful information. By the time a stub has been evicted 3 times, its note header is longer than its actual content for small stubs. This pattern was noted in 0009 recommendation 5 (cap eviction notes). The cap was added to the TODO list but is not yet implemented.

**Recommendation:** Cap eviction notes to 2 entries, collapsing older entries into "Evicted N times previously" — already tracked as a TODO. Separately, evaluate whether mechanical eviction notes provide any retrieval value to the model at all. If the model doesn't use them to make better decisions, remove them from the injected fragment header entirely and track them in a separate debug-only log.

## 6. Benchmark crates (caw-bench) consistently crowd out architecture stubs for "what is opencaw" queries (medium)

For every "what is opencaw" or "what can you do with opencaw" query, `caw-bench/src/opencaw.rs`, `caw-bench/src/runner.rs`, and `caw-bench/src/main.rs` appear in the top retrieved stubs. These are the self-referential benchmark files that contain the word "opencaw" dozens of times. Meanwhile, the canonical architecture overview (`README.md`, `SCOPE.md`, `context-as-workspace.md`) often appears as search-candidates or late in the retrieval sequence.

The benchmark files score high semantically because they reference every major OpenCAW concept (recall, orchestration, retrieval, sessions) in their Q&A dataset and runner code. But they describe the benchmark harness, not the system architecture. The model ends up describing OpenCAW's benchmarking infrastructure as a primary capability rather than leading with the core workspace context augmentation concept.

**Recommendation:** Add a negative boost (score penalty) for stubs in the `caw-bench/` subtree when the query does not contain benchmarking-specific terms ("benchmark", "score", "niah", "workload", "precision", "recall@k"). Architecture queries should not retrieve benchmark implementation details unless explicitly requested.

Where the retrieved context covers the query — architecture overview, crate capabilities, curation pipeline structure — the model's answers are specific, accurate, and cite concrete code structures (struct names, function signatures, crate paths). No fake `[recalled from ...]` markers were generated in any of the three sessions, confirming the B6 strip_markers fix is effective.

## 9. Three rapid-succession sessions with identical questions compound B7 geometrically (observation)

Sessions 071921, 072123, and 072432 all asked the same two opening questions and ran within 13 minutes of each other. Each session's responses were indexed into the in-memory HNSW before the next session started. By session 072432, the retrieval pool contained prior-session responses from two preceding sessions. The B7 contamination doubles with each additional session on the same topic.

This means the problem is not just about one prior session bleeding in — it's about accumulating all prior sessions. In a realistic multi-hour work session where a developer asks the same type of questions repeatedly, B7 would cause the context to be dominated by the accumulated responses of earlier micro-sessions, with real workspace content pushed to the margins.

**Recommendation:** The in-memory HNSW should be cleared or have its session-derived embeddings expire after a configurable TTL (e.g., 30 minutes). Alternatively, prior-session stubs should be tagged with their session timestamp and deprioritized when the embedding time is within the current session window.
