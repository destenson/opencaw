# QA Recommendations — Loop 0001

Generated from analysis of `.caw0001/index.db` (699 stubs, 0 stale, 0 ignored, 0 consolidation notes).

---

## 1. Embedding text is triple-redundant for code chunks (Critical)

**What:** `SemanticRetriever::insert` builds embed text as `path + " " + summary + " " + outline.join(" ")`. For a chunked code file, the summary is already `"Chunk N/M of path: contains fn_x, fn_y — Defines: fn_x, fn_y"`. So the embed string looks like:

```
./crates/caw-core/src/lib.rs  Chunk 3/42 of ./crates/caw-core/src/lib.rs: contains pub struct Foo, impl Foo — Defines: pub struct Foo, impl Foo  pub struct Foo impl Foo ...
```

The path appears twice. The function names appear three times. BGE-small has a 512-token context limit. For stubs with long outlines (e.g. the `caw-core/src/lib.rs` stubs that carry 5+ multi-line signatures), this repetition consumes a significant fraction of the embedding budget with no information gain.

**Why it matters:** Semantic similarity depends on what tokens the embedder sees. Redundant repetitions of the same symbols suppress sensitivity to other tokens in the string — the model's attention saturates on repeated items. A query about what a function *does* (not just its name) gets crowded out.

**Where:** `crates/caw-index/src/lib.rs:89` for `SemanticRetriever::insert`; also `crates/caw-index/src/lib.rs:411` for the parallel path. The summary duplication originates in `crates/caw-ingest/src/lib.rs:158-159` where `chunk_summary` and `summarize_code` are combined without deduplication.

**Fix direction:** The embed text should be a single coherent sentence: `path + " " + compact_summary`. The outline entries should not be appended verbatim — they are already baked into the summary. Alternatively, embed the chunk content directly (rather than only metadata) for code stubs, and use the summary only at query time.

## 2. 36% of stubs (254/699) carry no outline and embed nearly zero semantic signal (Critical)

**What:** `SELECT COUNT(*) FROM stubs WHERE outline = '[]'` returns 254. These are overwhelmingly tail chunks — the last chunk of a multi-chunk file after all symbol-bearing lines have been attributed to earlier chunks. Their summaries are raw code snippets like:

```
Chunk 20/20 of ./crates/caw-bench/src/runner.rs — let pass = answer.to_lowercase().contains(&needle.to_lowercase());
```

The embed string for this stub: `./crates/caw-bench/src/runner.rs Chunk 20/20 of ./crates/caw-bench/src/runner.rs — let pass = answer.to_lowercase().contains(&needle.to_lowercase());`

The only unique content is a single code expression. A query about "how test answers are evaluated" cannot possibly surface this stub through semantic similarity — the snippet has no meaning without context.

**Why it matters:** Tail chunks often contain the return statements, error branches, and closing logic of functions. These are not trivially ignorable. A query about error handling, test pass/fail logic, or cleanup code will miss exactly this content. The system has effectively indexed these stubs in a way that makes them permanently unreachable.

**Where:** `crates/caw-ingest/src/chunking.rs:228-252` (`chunk_summary`) produces the fallback "first non-empty code line" summary when `outline_entries` is empty. `crates/caw-ingest/src/lib.rs:140-158` is where the chunk-level summarizer is called with an empty outline.

**Fix direction:** For tail chunks with empty outlines, fall back to embedding the chunk's actual text content rather than the positional header. The embed path at `crates/caw-index/src/lib.rs:89` skips content because "at this layer we don't have it" — but the ingestion path does have it, and the bench index embeds content directly. The CLI/default path should do the same.

## 3. Runtime session files (.caw/) are being indexed (High)

**What:** 9 stubs belong to `.caw/session-20260508-*.md`. These are conversation transcripts written by the orchestrator during a session. They contain prior-session Q&A about opencaw — content like "Turn 1: [User]: what can you do with opencaw?" and "Turn 2: [User]: is opencaw development completed?".

**Why it matters:** These files semantically overlap with real documentation. A query about "multi-turn conversations" or "what opencaw can do" will surface session transcripts instead of (or alongside) the relevant code and design docs. The retriever cannot distinguish "this is documentation about multi-turn support" from "this is a recorded session where multi-turn support was discussed." Session content pollutes precision.

**Where:** `.cawignore` (if it exists) or the `should_skip` predicate at `crates/caw-ingest/src/lib.rs:387`. The `.caw` directory is not excluded by the current skip list.

**Fix direction:** Add `.caw` (and `.caw0001`, etc.) to `should_skip` or to the generated `.cawignore`. Session files are ephemeral artifacts produced by the system — they should never be indexed as corpus content.

## 4. Dependency and config files embed as their first line, not their content (High)

**What:** TOML, YAML, and JSON files are classified as `PlainText`, so `summarize_plaintext` is called, which returns `truncate_str(first_line, 200)`. For `Cargo.toml`, split into 3 chunks, the summaries are:

- Chunk 1: `"[workspace]"` 
- Chunk 2: `"tracing = \"0.1\""` 
- Chunk 3: `"edition.workspace = true"`

**Why it matters:** The most retrieval-relevant question for a `Cargo.toml` is "what crates/features does this workspace use?" — e.g. "does opencaw support qdrant?" or "what embedding library is the default?". None of the three stub summaries carry that signal. A similarity search for "fastembed dependency" cannot surface the chunk that actually contains the `fastembed` entry because its summary says only `tracing = "0.1"`.

**Where:** `crates/caw-ingest/src/lib.rs:377` classifies `.toml`/`.yaml`/`.json` as `PlainText`. `crates/caw-ingest/src/summarizer.rs:118-124` dispatches to `summarize_plaintext` for this kind.

**Fix direction:** Either add a `Config` or `Structured` content kind with a summarizer that extracts key names/values (dependency names, feature flags, top-level keys), or treat these files as Markdown-like and extract their section headers. At minimum, the summarizer should scan more than the first line for structured files.

## 5. Consolidation notes are empty — no cross-turn learning is persisting (High)

**What:** `SELECT COUNT(*) FROM consolidation_notes` returns 0. Zero eviction notes were written during loop 0001.

**Why it matters:** Consolidation is opencaw's mechanism for preserving what was learned from a context fragment after it's evicted from the active workspace. Without notes, every turn starts from scratch — the system cannot use "last session I learned that X" style recall. If loop 0001 was a multi-turn session and no consolidation fired, it means either (a) no fragments were evicted (the budget was never exhausted), or (b) the consolidation path is wired to `MechanicalConsolidation` which writes format strings that are not being persisted to the DB, or (c) consolidation is only triggered on explicit eviction which never happened because the orchestrator ran to completion without hitting the budget ceiling.

**Where:** `crates/caw-orchestrator/src/consolidation.rs`. The `synthesize_eviction_note` API exists but the orchestrator's `do_recall` function at `crates/caw-orchestrator/src/lib.rs:163` calls `scheduler.schedule` which may evict fragments from `loaded`, but there is no call to `ConsolidationSynthesizer` in `do_recall`. Eviction and consolidation are decoupled — eviction happens in the scheduler, consolidation must be wired in somewhere above it, and in this run it either wasn't wired or didn't fire.

**Fix direction:** Audit whether `ConsolidationSynthesizer::synthesize_eviction_note` is being called anywhere in the production path. If not, the consolidation infrastructure exists but is not connected. Connect it in `do_recall` when `decision.evicted` is non-empty.

## 6. `chunk_summary` and `summarize_code` produce redundant combined summaries (Medium)

**What:** For a code chunk with outline entries, the final stored summary is `"{chunk_summary} — {base_summary}"` which looks like:

```
Chunk 3/5 of ./examples/ollama_demo.rs: contains fn main() -> Result<()> — Defines: fn main() -> Result<()>
```

The symbol `fn main() -> Result<()>` appears twice in the same string. For chunks with multiple symbols the duplication is proportionally larger.

**Why it matters:** Stored in the `summary` field and embedded at retrieval time, this doubles the token cost of symbol names in the embedding. It's also noisy when the summary is shown to the model as part of context guidance.

**Where:** `crates/caw-ingest/src/lib.rs:153-159` — the `format!("{} — {}", position_summary, base_summary)` branch.

**Fix direction:** If `position_summary` already contains the symbol names (it does, via "contains fn_x, fn_y"), skip the base summary entirely and use only the position summary. Or rewrite so that `position_summary` carries only chunk position ("Chunk 3/5 of path") and the base summary carries only semantic content.

## 7. `caw-core/src/lib.rs` fragmented into 42 chunks — file is too large to retrieve coherently (Medium)

**What:** The path `./crates/caw-core/src/lib.rs` has 42 stubs in the DB. At the chunk level, retrieval for any single concept in this file must hope the correct one of 42 chunks surfaces above the threshold. A query about the `Stub` type would need to match the right chunk among 42.

**Why it matters:** Highly fragmented files degrade recall precision. The embeddings for adjacent chunks (e.g. chunk 10 and chunk 11 of `caw-core/src/lib.rs`) will have very similar semantic content because they're both "core type definitions" — but retrieval returns only the top-k, so many relevant chunks will be below the threshold even when the file is clearly relevant.

**Where:** The file itself; caw-core/src/lib.rs appears to be a monolith. This is a code organization issue, not purely an indexing issue — but indexing exposes it.

**Fix direction:** Split `caw-core/src/lib.rs` into focused modules. At the indexing level, consider a file-level aggregation heuristic: if a file produces more than N chunks, emit one additional "file-level" stub whose summary is derived from the full outline, to serve as a coarse routing stub.

## 8. Outline entry substring matching is brittle for multi-line signatures (Low)

**What:** `outline_entries_for_chunk` at `crates/caw-ingest/src/chunking.rs:372` checks `chunk_text.contains(entry.as_str())`. Outline entries for Rust include full multi-line function signatures verbatim from tree-sitter, e.g.:

```
fn from_bpe(
        result: Result<tiktoken_rs::CoreBPE, impl std::fmt::Display>,
        name: &'static str,
    ) -> CawResult<Self>
```

Because chunking splits at line boundaries, a chunk that contains lines 2-N of this signature but not line 1 will fail the `contains` check. That chunk will show `outline_entries: []` even though it does contain most of the function body.

**Why it matters:** Empty outline entries cascade into lower-quality summaries (problem 2) and degraded embedding signal.

**Where:** `crates/caw-ingest/src/chunking.rs:372-378`. Also `crates/caw-ingest/src/tree_sitter_outline.rs` (not read but is the source of these multi-line entries).

**Fix direction:** Match on the function/symbol name only (first token of the entry up to `(`) rather than the full multi-line signature. This would correctly attribute a chunk that contains the body of a function even if its signature begins in the previous chunk.

## 9. Cargo.toml and small config files are chunked unnecessarily (Low)

**What:** `Cargo.toml` (a workspace manifest) is split into 3 chunks. Each chunk's summary is a single config line. The file is being chunked because its `cheap_token_upper_bound` exceeds 500, not because the content is semantically divisible.

**Why it matters:** Three stubs for one config file consumes index space and creates retrieval surface area that returns low-quality results. No meaningful semantic distinction exists between "the chunk with `[workspace]`" and "the chunk with `fastembed = ...`" for any realistic query.

**Where:** `crates/caw-ingest/src/chunking.rs:27-49` (`ChunkingConfig::default`). The `token_threshold: 500` applies uniformly to all file types.

**Fix direction:** Either raise the chunking threshold for `PlainText`/config files, or skip chunking when `kind == PlainText` and the file is a manifest format (TOML/YAML/JSON). Config files benefit from being kept whole: a single stub with a summary of key entries beats three stubs each summarizing one line.
