# QA Loop 0003 — Recommendations

Generated from: `.caw0003/index.db`, three sessions (050545, 050942, 051313), 17–18 prompt files each.

---

## 1. Multi-pass recall produces massively corrupted context

**Severity: critical**

Prompt `prompt-20260508-050942-turn-8.txt` (the "is opencaw development completed?" answer turn) reveals what multi-pass recall actually produces: over 200 truncated and repeatedly duplicated `[recalled from ...]` fragments from a single file. `crates/caw-orchestrator/src/lib.rs` is recalled approximately 30 times in one prompt, with fragments cut off mid-expression (`[recalled from ./crates/caw-orchestr`, `[recalled from ./cr`, `[recalled from ./crates/c`). Source paths are corrupted — one fragment reads `[recalled from max_recall_iterations = 3,` where the source path has been replaced with code content. Invalid Rust appears in content: `struct S: BudgetScheduler,` (the trait bound is rendered as a struct keyword). The pattern is consistent: each thinking-trace step fires retrieval, which re-retrieves overlapping chunks of the same large file, and the formatter interleaves them without deduplication or truncation guards.

The model receives a 1225-token context that is essentially unreadable: repeated partial views of the same functions, broken locators, and no coherent narrative. This is the primary reason answers in session 050942 are worse than session 050545 (which used search-candidates mode and got cleaner context). The multi-pass recall loop is actively harmful for this model and this index.

**Fix:** enforce strict per-source deduplication in the workspace formatter — once a stub_id has been admitted, subsequent retrieval of the same stub_id should update relevance score, not append another fragment. Add a truncation floor for fragment content (never emit a fragment smaller than N tokens). Validate that the source path field cannot contain embedded content.

## 2. Stale stub summaries cause incorrect status reporting

**Severity: high**

The stub for `TODO.md` chunk 4/10 is indexed with summary "contains Provenance, Mid-Session Annotation, Prompt Transformer, Orchestration." These items are largely complete in the current codebase. When the model answers "what's next to work on?" it reports these as outstanding tasks — sourcing a factually wrong answer from a stub that was accurate when generated but has since drifted. The same stub is retrieved identically across all three sessions for any status query, so all sessions give the same stale answer.

This is a manifestation of the indexing-freshness problem: stubs are generated once and not re-summarized when the file changes. The `TODO.md` file has evolved significantly (many items checked off), but the stub still reflects its old state.

**Fix:** either re-index modified files on each session start (the `StubStore::get_by_content_hash` mechanism exists for exactly this), or invalidate stubs whose source file mtime has changed. For files whose content changes frequently (`TODO.md`, session logs), re-summarization should happen automatically before retrieval.

## 3. Holistic file queries retrieve only one chunk, making count/status queries unanswerable

**Severity: high**

When asked "how many todo's are left?", the retrieval surface only chunk 4/10 of `TODO.md`. The model correctly reports that it cannot answer — it sees a partial list with no completion markers and no information about the other 9 chunks. The same pattern holds for any query requiring whole-document understanding (count of open items, full status, complete list of components).

The `is_status_request` and `is_next_step_request` intent classifier flags exist precisely to handle this, but they aren't wired to retrieval. When either flag fires and the top-k results are fragments of the same file, the system should load the remaining chunks of that file rather than stopping at top-k hits.

**Fix:** when `is_status_request` or `is_next_step_request` is set and the top retrieved stub belongs to a file with N > 1 chunks, greedily load all chunks of that file up to a token budget. For project management documents (TODO.md, SCOPE.md, codebase-review-report.md), this is the correct behavior for nearly all queries about them.

## 4. Prior session logs are indexed and propagate hallucinations across sessions

**Severity: high**

Session log files from `.caw/session-*.md` are included in the retrieval index and recalled into subsequent sessions. In session 050942, the session-050545 log was included as a fragment in 8 out of 8 prompts. This creates a feedback loop: the model's prior responses become retrieval-weighted evidence for future answers.

Concretely: the session-050545 log contains the hallucination "there are many chunks (e.g., 34 chunks from a single file `dynamic.rs`)" — a claim the model in session 050545 made without any supporting context. When session 050942 is asked to reason about status or development, this hallucination appears in its context (visible in turn-8's prompt), and the model answers partly from it. This is how a single fabricated detail spreads across sessions and becomes a retrieval-weighted "fact."

This issue was flagged in 0002 (observation 6). The `.caw/` skip filter evidently isn't working when indexing for these sessions.

**Fix:** confirm and fix the `.caw/` directory skip in the indexing path. Session logs should never enter the retrieval index. If cross-session context is desired, it should go through the explicit consolidation-notes mechanism, not raw session file indexing.

## 5. Model hallucinates specific details not present in injected context

**Severity: high**

In session 050545 turn 2, the model receives 701 tokens of search-candidates metadata (a list of ~12 stub summaries with no loaded content), then claims: "there are many chunks (e.g., 34 chunks from a single file `dynamic.rs`)." The 34-chunk count for `dynamic.rs` is not in the injected context — it is not derivable from the stub list shown. The model is filling in from its general training signal about RAG systems rather than reasoning from evidence.

This is a retrieval quality indicator: when the injected context is too sparse to answer the question, the model invents plausible-sounding but ungrounded details. The search-candidates "discovery metadata" mode is intended to let the model request files, but in the QA harness there is no mechanism for the model to actually do that. The result is a model left with insufficient context and a tendency to confabulate.

**Fix:** don't present the model with search-candidates-only context for substantive questions — either load the top-k candidates directly, or don't send the query to the model at all. Search-candidates mode is only useful if the model can interactively request full content, which requires a tool-call loop. In a single-turn QA setting, it's worse than just loading the top candidates.

## 6. Casual user messages interpreted as queries, producing off-topic responses

**Severity: medium**

In session 050545 turn 3, the user says "nice to know" (a casual acknowledgment of the previous answer). The intent classifier correctly classifies all flags as false. However, the retrieval system still fetches lexically-overlapping content — SCOPE.md and TODO.md chunks containing "nice to have" language — and the model produces a substantive response about nice-to-have features. The model is answering a question that wasn't asked.

The pattern: classifier says "not a meaningful query," but retrieval still runs and surfaces semantically close but contextually wrong fragments, and the model answers them.

**Fix:** when the intent classifier returns all-false and the user message is short (< ~15 tokens), skip retrieval entirely and prompt the model to ask for clarification or acknowledge the input. A low-information input should produce a low-information response (acknowledgment), not a full retrieval cycle.

## 7. Zero consolidation notes produced across all three sessions

**Severity: medium**

Same finding as 0002: the `consolidation_notes` table has 0 rows despite three sessions with 8–18 prompt turns each. Eviction-triggered consolidation either isn't firing or isn't persisting. Without consolidation notes, there is no cross-turn memory — the model receives no signal about what was learned in earlier turns when later turns retrieve the same stubs.

This matters most in sessions 050942 and 051313, which span 9+ user turns. By turn 6, the model has no access to what was established in turns 1–3 except through the full session history (which isn't included in the context format used here).

**Fix:** add a diagnostic count to the CLI — log how many evictions fired, how many consolidation notes were generated, and how many were persisted to the store. This is the minimal instrumentation needed to know whether the path is broken or just never triggered.

## 8. Retrieved context varies by factor of 8× for identical queries across sessions

**Severity: medium**

The query "what can you do with opencaw?" receives 403 tokens / 7 fragments in session 051313 turn 1 and 3,248 tokens / 43 fragments in session 050942 turn 4. The question is identical. The index is the same DB. The 8× variation suggests that session state (previously admitted fragments, prior retrieval, or random seed variation in HNSW) is substantially influencing retrieval — not just query-to-stub similarity.

This makes retrieval quality non-reproducible. Two runs of the same query in the same session are expected to differ as the workspace evolves, but cold-start retrieval for the same query should be deterministic.

**Fix:** investigate whether the `HnswVectorIndex` search has non-determinism in its approximate search (the instant_distance HNSW crate has an `ef_search` parameter affecting quality/speed tradeoff that may vary by graph state). If the index is rebuilt per session, build order may matter. Use `FlatVectorIndex` for determinism verification, then accept HNSW non-determinism only if it's bounded.

## 9. Session log markdown files are truncated — most turns not recorded

**Severity: medium**

Sessions with 18 prompt files produce only 3 turns in the session `.md` log. Session 050942 has 18 prompt files (representing roughly 9 user turns, counting both classifier and answer calls) but the session log `session-20260508-050942.md` contains only turns 1–3. The model's answers for turns 4–9 are not in the session log for review. The same truncation appears in session 051313.

This means QA analysis from session logs misses most of the session. Evaluators who rely on session markdown files get an incomplete picture of system behavior.

**Fix:** diagnose whether the session log writer exits early (error, SIGTERM, or bug), or whether the markdown file is not flushed before the process exits. The QA harness should flush session logs after every turn, not at session end.

## 10. Cargo.toml and empty stubs consume retrieval slots with zero signal (carry-forward from 0002)

**Severity: low**

Three-token stubs (`[package]` from `crates/caw-transform/Cargo.toml`, `crates/caw-curation/Cargo.toml`, `crates/caw-eval/Cargo.toml`) appear in prompt contexts for queries they cannot help answer. Each one displaces a useful fragment. This was flagged in 0002 and is still present in this index. TOML config files should be excluded or summarized with actual package-name extraction rather than the raw `[package]` header line.
