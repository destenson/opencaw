# QA Loop 0006 — Recommendations

Generated from: `.caw0006/index.db`, three sessions (062954, 063242, 063609), 13–18 prompt files each.

Sessions ran with model `Qwen3.6-35B-A3B-UD-Q2_K_XL`. All three sessions shared the same opening question sequence: "what is opencaw / what can you do with opencaw?" followed by status/inventory follow-ups and a caw-curation improvement query.

---

## 1. Model emits fake `[recalled from ...]` markers as part of its answer (B6)

**Severity: critical**

In `session-063609`, turn 14's response to "what can we do to improve on the caw-curation crate?" contains hundreds of lines like:

```
[recalled from ./crates/caw-orchestrator/src/thinking_trace.rs]
use caw_core::{
    BudgetScheduler, CawResult, ...
```

followed by verbatim source code. This is not injected context — it is generated output. The model learned the `[recalled from path]` marker format from its context and is using it as a generation pattern to structure its answer. The output mimics the context injection format exactly, interleaved with `<details>` / `<summary>` blocks and real Rust code transcribed from its training data.

This is dangerous: downstream parsing of prompt logs (or a sufficiently naive consumer) cannot distinguish model-generated `[recalled from]` text from actual retrieval output. The model is also using the injection format as a scratch pad for its own generation rather than answering the question — the actual answer to "what can we improve?" is buried or absent.

The root cause is that the provenance format is injected verbatim into every context block and the model has seen enough of it to replicate it. Mitigations:
- Use a format the model is unlikely to generate spontaneously (e.g., a UUID-delimited tag, or XML namespaced to a non-standard prefix).
- Add a post-processing step that detects `[recalled from ...]` in model output and flags or strips it before logging.
- The multi-pass recall system should detect when the model's output length is dominated by fake recall markers and abort the turn.

## 2. TODO.md inventory retrieval fails: only the trailing empty chunk is loaded

**Severity: high**

Every session that asks "how many todo's are left?" retrieves only `./TODO.md Chunk 14/14`, which has summary `contains TODO` and outline `TODO` — no actual content. The 13 substantive chunks (chunks 1–13, each 400–480 tokens with real TODO items) are never loaded.

Evidence: `prompt-20260508-063242-turn-17.txt` shows the final retry state: workspace contains `./TODO.md Chunk 14/14 | 16 tokens` alongside unrelated fragments from `caw-bench/src/bin/build_index.rs`, `caw-index/src/storage/sqlite_store.rs`, etc. The model correctly acknowledges it cannot answer ("The context only indicates that the file 'contains TODO'") rather than hallucinating a count.

The intent classifier correctly identifies the query as `is_inventory_request: true, is_status_request: true` (confirmed in `prompt-turn-12.txt`). The problem is that `AugmentationSignals` is detected but not acted on — as already noted in TODO.md, intent-driven proactive context injection is not yet wired into the retrieval path.

Why chunk 14 and not chunk 1? Chunk 14's summary (`contains TODO`) is semantically closest to the query string "how many todo's are left?" because it mentions TODO directly. Chunks 1–13 have summaries like "contains TODO, Retrieval, Ingestion & Indexing" — the extra terms dilute the match. This is a retrieval ranking artifact: the most uninformative chunk ranks highest for a query about the file itself.

The fix requires wiring augmentation signals: when `is_inventory_request` is true and the top hit is a partial chunk of a known status file, load all remaining chunks of that file up to the budget before running the answer model.

## 3. Session history is injected as multiple overlapping sliding-window fragments

**Severity: high**

Session history arrives in the workspace as 3–6 separate `[fragment: session history | XXX tokens]` fragments per turn, each containing a different sliding window of prior conversation. In `prompt-063242-turn-3.txt` (3520 total tokens across 22 fragments), three session history fragments account for 339 + 387 + 435 = 1161 tokens — 33% of the workspace — all containing heavily overlapping content from the same prior turn.

By turn 14 of session-063609, session history fragments occupy approximately 1600 of 4432 tokens. Each fragment is a different window cut of prior assistant responses, so the overlap is high. The model is reading the same sentences multiple times in a single prompt.

This wastes context budget, dilutes the relevance signal for other fragments, and creates a feedback loop where longer assistant responses in prior turns consume proportionally more workspace in subsequent turns.

The fix: session history should be deduplicated before injection. At minimum, a single contiguous session history fragment covering the full prior turns (with trimming at a budget ceiling) is better than multiple overlapping windows. Even better: use the `HistorySummarizer` already implemented in `caw-curation` to compress history when it exceeds a fraction of the token budget.

## 4. Eviction thrashing at scores 0.45–0.55 destroys recently-relevant content

**Severity: medium**

Consolidation notes show 247 eviction events across three sessions, with eviction scores clustering at 0.45–0.55. Many of these fragments are re-retrieved within 1–2 turns. For example, `caw-orchestrator/src/probe_recall.rs` is evicted with score 0.52 during turn 1 of session-062954 and then appears again in the workspace for turn 3.

With a default relevance decay rate of 0.8 per step, a fragment admitted at retrieval score 0.7 decays to:
- Step 1: 0.56
- Step 2: 0.45

Both are below the default unload threshold (0.5), meaning a document admitted as "relevant" can be evicted after just two reasoning steps with no re-engagement. For conversational sessions where the same concepts recur every few turns, this is counterproductive: the system evicts, re-retrieves, re-evicts in a cycle.

The `HysteresisAnalysis` tool in `caw-eval` is designed to detect exactly this pattern. It is not being invoked in QA loops. Recommendation: run `HysteresisAnalysis` on each session's `SessionEvaluator` output and log the result; use it to suggest threshold adjustments. A first concrete fix: raise the unload threshold floor from 0.5 to 0.35 for documents that have been admitted at least twice in the same session (indicating persistent relevance despite decay).

## 5. Consolidation notes are eviction metadata only — no knowledge extraction

**Severity: medium**

All 247 consolidation notes in `.caw0006/index.db` are of the form:

> Evicted (relevance decayed to 0.52) during query about '...'. Source: ./path/to/file.rs

This is eviction bookkeeping, not synthesized knowledge. The notes tell the model *that* something was evicted; they do not record *what was learned* from it. When a fragment is re-recalled and the note is prepended, the model reads "this was evicted before" — which adds noise rather than signal.

`LlmConsolidation` exists in `caw-curation` to produce meaningful synthesis (conclusions, decisions, key facts) but `MechanicalConsolidation` is the default. The CLI option `--llm-consolidation` exists but is not used in QA sessions.

Even without LLM synthesis, the mechanical default should at minimum include the evicted stub's summary text, so the model knows the topic of what was evicted. The current note format strips all content and retains only the score and source path.

## 6. caw-bench implementation files crowd out architecture documentation in architecture queries

**Severity: medium**

For every architecture/overview query ("what is opencaw?", "what can you do?", "is development completed?"), the workspace includes multiple chunks from `caw-bench/src/bin/tune.rs`, `caw-bench/src/bin/coop.rs`, `caw-bench/src/runner.rs`, `caw-bench/src/intent.rs`, and `caw-bench/src/bin/intent_bench.rs`. These are benchmarking harness implementation files — not documentation.

The problem is semantic: the bench files contain terms like "opencaw", "recall", "retrieval", "context", "workspace" throughout, which match every architecture query. Meanwhile, `context-as-workspace.md` (the design spec) and `SCOPE.md` are retrieved sparsely or not at all.

For a "what is X?" query, documentation sources should rank above implementation files. One approach: weight stubs from `*.md` files higher when `wants_explanation: true` is set by the intent classifier — or implement a document-type tier in the retrieval ranking so design docs score above source code for explanatory queries.

## 7. Trailing code chunk fragments (single lines, closing braces) survive the 10-token filter

**Severity: low**

`crates/caw-orchestrator/src/dynamic.rs Chunk 9/35` (content: `}`, 22 tokens) appears in multiple session workspaces for unrelated queries. It consistently scores well enough to survive retrieval despite containing only a closing brace. The 10-token minimum-content filter removed the most degenerate stubs (3-token `[package]` Cargo.toml fragments), but 22-token single-expression or single-closing-brace chunks still pass.

The fix from TODO.md ("fall back to a description derived from the parent file stub's summary when chunk content is below semantic threshold") is the right approach. A heuristic: if a chunk's non-whitespace, non-punctuation character ratio is below some threshold (e.g., fewer than 5 distinct alphabetic tokens), replace its retrieval representation with the parent file's first chunk summary. This prevents pure-structural fragments from consuming workspace budget.
