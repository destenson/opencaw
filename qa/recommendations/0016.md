## Observations (prioritized)

### 1. (Critical) Degenerate model output on initial completion — session records blank answer

Turn-3 prompt response: `Error: degenerate output from Qwen3.6-35B-A3B-UD-Q2_K_XL: OpenCAW (Context as Workspace) is a framework that treats the workspace...`

The first 120 chars of the response are a correct answer. The `is_looping` function fired on something later in the response (word-dominance, trigram collapse, or line-repetition check). This is probably a genuine loop — Q2_K_XL quantization at 3B active MoE params is aggressive, and the model appears to start correctly then repeat itself under a 1700-token context.

B15 is working: the turn IS written before the error propagates. But `run_turn` creates `CompletionResponse { answer: String::new() }` for the degenerate case, so the session log records an empty assistant response rather than the valid prefix. The valid opening ("OpenCAW (Context as Workspace) is a framework...") is discarded entirely.

**Impact**: Every session with this model at this quantization level produces 0 useful turns. The user sees nothing, and the session log accumulates only evidence of failure.

### 2. (High) Search-candidates turn produces blank response despite "always respond" instruction

Turn-2 prompt (575 tokens, 1 fragment = search candidate list) has a blank response (""). The system prompt includes: "A blank or empty response is never acceptable." The model still returned blank. The most likely cause: the model emitted a `<think>...</think>` block reasoning about the candidates, followed by an empty answer. `split_thinking` correctly extracts `answer = ""`, and `is_looping("")` returns false (len < 20), so no degenerate error — the blank answer passes through silently.

This is B8 manifesting on the search-candidates pass specifically. The "always respond" instruction is in the system prompt but is not enforced by the system — there is no check that catches a blank answer before writing the turn.

**Impact**: When the search-candidates pass produces a blank, the orchestrator then re-completes with the full context (turn 3). That re-completion is the one that degenerated. Had the blank been caught and treated as a degenerate, the retry logic could have applied sooner.

### 4. (High) README.md chunk retrieved as outline skeleton — no explanatory content

`./README.md chunk 1/12` is loaded at 50 tokens with: `Outline: OpenCAW - Context as Workspace, Architecture, Crates, Anthropic, Groq, ClaudeCode` — this is a section-heading skeleton with no prose. The actual explanation of what opencaw is and why to use it lives in the body text of README.md, which is in chunks 2–4 (each ~496 tokens per the stubs table). None of those were retrieved.

This is the second half of the issue flagged in QA 0015 recommendation 5 (load documentation stubs in full-content mode for `wants_explanation` queries). The retriever correctly identifies README.md as the most relevant source, then injects only its structural outline. The model sees "Architecture, Crates, Anthropic" and cannot explain the system.

**Impact**: README.md is retrieved for every conceptual query, but in a form that provides no usable context. The retrieval is not wrong; the content mode is.

### 5. (Medium) Valid partial answer from a degenerate response is discarded

The error sample in the degenerate error ("OpenCAW (Context as Workspace) is a framework that treats the workspace...") is the first 120 chars of the answer after `split_thinking` runs. This is a coherent, correct opening. The response looped somewhere after that. The current code stores `String::new()` as the answer, throwing away the valid prefix.

For aggressively quantized models that start correctly and loop partway through, the valid prefix is often sufficient to answer the user. The `is_looping` checks (trigram diversity, line repetition) could identify *where* the loop starts and truncate there, rather than treating the entire response as worthless.

### 6. (Medium) Zero consolidation notes — insight accumulation blocked on degenerate sessions

`SELECT COUNT(*) FROM consolidation_notes` returns 0. Consolidation fires on eviction, which requires multi-turn sessions where fragments accumulate and then age out. A session that degenerates on turn 1 never reaches eviction and contributes nothing to the cross-session note store.

If the target model consistently degenerates (as this quantization level does), the system never builds cross-session memory. The "learning from use" loop requires working sessions.

### 7. (Low) Q2_K_XL quantization of a 3B-active-param MoE is too lossy for reliable 1700-token contexts

`Qwen3.6-35B-A3B` activates only ~3B parameters per token in MoE routing. At Q2_K_XL quantization this is equivalent to a small model heavily quantized. Generating a coherent ~400-token answer in a 1700-token context is plausible on first tokens but the repetition pattern suggests the model's attention mechanism is degrading under quantization pressure. The degenerate detection is almost certainly firing correctly here, not as a false positive (unlike B13/B14 which were genuine false positives).

Recommendation: use at minimum Q4_K_M for this architecture at this context length. Alternatively, a dense Qwen3-8B at Q5 may be more reliable for this task.

### 8. (Low) Single-turn failed session yields no multi-turn QA signal

The 0016 session has exactly 1 user turn, which fails before producing an answer. Nothing can be observed about: context accumulation across turns, eviction behavior, retrieval quality at turn 2+, session continuity with prior sessions, probe behavior, or annotation behavior. The QA harness does not detect or log this condition specially.
