## 1. B00 is still active — session aborted on the first question (critical)

The model's response to "what is opencaw and why should I use it?" was degenerate Rust code:
`").unwrap()); static ANNOTATION_PATTERN: LazyLock<Regex> = LazyLock::new(|| Regex::new(r#"<note id="([^"]+)">(.*?)</...`

This is verbatim source from `crates/caw-transform/src/recall.rs:6-10`. The model generated the tail of `PROBE_PATTERN.unwrap()` followed by the `ANNOTATION_PATTERN` declaration — it was pattern-completing Rust source, not answering the question.

This is the exact error string documented in B00 ("REGRESSION: caw-cli failed on first run"). B00 remains unfixed. Every QA session on this model will abort immediately until B00 is resolved. Turns 2 and 3 were never reached.

The degenerate content starts mid-expression (`").unwrap());`) which rules out a simple empty prompt or missing system prompt — the model was mid-generation in what looks like a code completion context. The prompt (turn-2.txt) shows a valid system prompt and user query, so the issue is model-side: the model is generating code instead of prose. Whether this is training-data leakage or context contamination from indexed recall.rs stubs is unclear, but `caw-transform/src/recall.rs` is in the indexed workspace and contains `ANNOTATION_PATTERN` — a strong candidate for contamination.

**Action**: Investigate why `caw-transform/src/recall.rs` stubs would be retrievable for an explanation query about "what is opencaw?" — and whether a prior recall.rs stub in context is triggering the model to code-complete into it. Also check whether the degenerate-output retry logic (tracked as a TODO for "retries, not hard errors") would have caught this and retried.

## 2. For `wants_explanation` queries, no stub content reached the model — only search-candidates (high)

`prompt-turn-2.txt` shows a single fragment: `search-candidates | 294 tokens`. This is 6 file paths with one-line summaries. None of README.md, SCOPE.md, or any other stub was loaded into the workspace. The context the model received was purely discovery metadata.

The candidates listed were exactly the right files:
- `./README.md` — Chunk 1/12 (contains "OpenCAW - Context as Workspace, Architecture, Crates")
- `./SCOPE.md` — Chunk 1/4 (contains "Scope — OpenCAW v1, What v1 is")
- `./codebase-review-report.md` — Chunk 1/13 (executive summary)

These were identified as matches but not loaded. The system prompt for search-candidates mode tells the model: "Mention the specific files you need if you want them loaded" — but B4 documents that no infrastructure exists to fulfill such requests in the QA harness. The model received the right file list, was told it could request them, and had no way to actually get them.

The `wants_explanation` code path added in earlier loops (1.5× Markdown boost, Code stub cap) is apparently not preventing search-candidates mode from being used as the sole context. The 294-token fragment is low enough that loading even a single README chunk would have been within budget.

**Action**: For `wants_explanation=true`, treat search-candidates as insufficient context and force a second retrieval pass that actually loads the top-ranked candidate stubs. Do not hand the model a candidate list and tell it to ask for what it needs if the infrastructure cannot fulfill such requests.

## 4. The degenerate output implicates recall.rs stubs as a contamination vector (medium)

The model generated code specifically from `caw-transform/src/recall.rs` — the module that processes retrieval annotations and `<note>` tags. This file is part of the codebase and would be indexed. If a recall.rs stub was loaded into context (even as a low-relevance match), its code syntax could trigger the model to code-complete rather than answer in prose.

The search-candidates list did not include recall.rs — so the contamination, if context-based, came from a prior session's workspace state or from a stub that was loaded but not shown in the candidate list. The more parsimonious explanation is training-data leakage: the model has memorized opencaw source and is generating it when confused.

Either way, this points to the degenerate retry logic (see TODO: "Degenerate output should trigger retries, not hard errors") as the practical mitigation: a second attempt with a rephrased prompt would likely not reproduce this exact failure.
