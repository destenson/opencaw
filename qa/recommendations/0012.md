# QA Loop 0012 Recommendations

Sessions analyzed: 3 sessions (080106, 080400, 080631), 3 turns each, model Qwen3.6-35B-A3B-UD-Q2_K_XL.
Index: 677 stubs across 84 unique paths, 173 consolidation notes (all eviction).

---

## 1. B7 (prior session history flooding) is still active and is the dominant failure mode

**Evidence:** Session 080631 turn 1 had 1560/2694 workspace tokens (58%) consumed by two session-history fragments before a single workspace stub was loaded. Session 080400 turn 1 had similar proportions. Both session history fragments were model responses from a prior session on the same topic.

**Consequence:** For session 080631 turns 2 and 3, the workspace was already near budget capacity from history content. Turn 2's answer to "is opencaw development completed?" is nearly verbatim identical to session 080400 turn 2 — not because the retrieval found the same stubs, but because it retrieved session 080400's model *response*. Turn 3 ("what can we do to improve on caw-curation?") retrieved zero caw-curation stubs despite 17 caw-curation chunks in the index; the budget was occupied by history.

**Why it matters:** B7 turns opencaw into an echo chamber. Each session reinforces the prior session's answers regardless of what the workspace actually contains. This is worse than no history injection — it actively displaces workspace stubs with fabricated prior-session prose. The fix for B3 (in-memory only for session stubs) is in place but does not address the retrieval weight problem: model responses contain all relevant vocabulary in fluent prose, so they score higher than workspace stubs and are admitted first.

**Recommended action:** Cap session history's workspace budget share. History fragments should not be admitted if they would consume more than X% (suggested: 20-25%) of the total workspace budget. Treat history and workspace stubs as competing admission pools with separate budget envelopes.

## 2. caw-curation stubs completely absent from a query explicitly asking about caw-curation

**Evidence:** Session 080631 turn 3 ("what can we do to improve on the caw-curation crate?") produced zero caw-curation fragments. The index contains 17 caw-curation chunks (`pipeline.rs`, `history.rs`, `tool_output.rs`, `prompt_budget.rs`). The model stated: "there is no mention of a caw-curation crate in the current context."

**Root cause:** The 1560-token session history budget left room for only a handful of workspace stubs. Of the 11 fragments admitted, none matched caw-curation. This is a consequence of observation 1, but also reveals that BM25/semantic retrieval did not rank caw-curation stubs above the history fragments even after history consumed its share — meaning the retrieval signal for "improve caw-curation" did not match caw-curation stubs strongly enough to force admission.

**Secondary issue:** Chunk summaries for caw-curation files name the structs (`CurationPipeline`, `LlmHistorySummarizer`) without using the term "caw-curation" prominently. A query using the crate name as the primary key may not match stub summaries that never repeat it.

**Recommended action:** Two fixes needed: (a) address observation 1 (history budget cap), and (b) verify that crate-name terms appear in stubs for files under `crates/caw-curation/`. Either the crate path should be included in stub summaries, or a crate-level overview stub should exist that names the crate explicitly.

## 3. Fragment truncation / B1 corruption still producing noise in prompts

**Evidence:** The prompt for session 080106 turn 2 (the large prompt I read in full) contains 15–20 repeated occurrences of the same truncated string: `[recalled from ./crates/caw-orchestrator/src/dynamic.rs] "These annotations help the system remember what was relevant if the` — each an incomplete sentence fragment ending at a token boundary. These appear interleaved with real content throughout the context.

**Consequence:** The model receives repeated instances of identical partial text. Each instance consumes tokens without contributing information. The repetition likely reduces the effective context-to-noise ratio for that turn significantly. The model's turn-2 response (meta-evaluation of context quality) mentions "Redundancy" and "wall of text" — it's responding to this exact corruption.

**Why it matters:** B1 was documented as corrupting fragment source paths in multi-pass recall. What session 080106 turn-2 shows is that corruption still produces repeated near-identical strings that fill the context with noise. Whether this is the same code path or a related one needs investigation.

## 4. TODO.md inventory queries retrieve only the last chunk, missing the actual task list

**Evidence:** Session 080400 turn 3 ("how many todos are left?") retrieved chunk 22/22 of TODO.md — the final chunk, containing a description of a completed marker-stripping task. The model correctly diagnosed the problem ("I cannot provide a count, the retrieved context does not include the other chunks"). The intent classifier correctly set `is_inventory_request=true` for this query but that signal did not influence which TODO.md chunk was retrieved.

**Why this matters:** TODO.md has 22 chunks. BM25/semantic match on "how many todos are left?" landed on chunk 22/22 because that chunk mentions `- [x]` completion markers (the word "todo" appears there). The actual task list is in chunks 1–21. For inventory queries on multi-chunk documents, retrieval needs to either: (a) prefer earlier/overview chunks when `is_inventory_request` is set, or (b) use the document-level index stub approach already noted in TODO.md (the open task about document-level overview stubs for BUGS.md, TODO.md, SCOPE.md).

## 5. Model answers about project status are based on a partial, potentially stale BUGS.md view

**Evidence:** Both sessions 080400 and 080631 cited B0, B1, B2 as the known bugs. BUGS.md currently documents B3–B9 as well, with B2 and B5 marked fixed. The model is answering from a snapshot of BUGS.md that predates several additions. Chunk 1 of BUGS.md (which contains B0 and B1) scores high for any status query; chunks containing B3–B9 rank lower and weren't retrieved.

**Consequence:** A developer asking "what are the current bugs?" receives a materially incomplete answer — missing the highest-severity active bugs (B7, B8, B9). The incompleteness is invisible to the user because the model confidently presents what it has as a complete list.

**Recommended action:** Same as observation 4: a document-level overview stub for BUGS.md that contains section headings (B0 through B9) and their status. This would be boosted for status queries and give the model a map of the document before retrieving content.

## 6. Consolidation notes are all eviction-noise; none add semantic value

**Evidence:** All 173 consolidation notes in index.db follow the pattern: "Evicted (relevance decayed to 0.XX) during query about 'truncated query text'." They record the eviction event and score but nothing about why the fragment was relevant, what was learned from it, or how it relates to other stubs. These notes appear in prompt fragments and consume tokens without helping the model understand the stub's content.

**Consequence:** The prior-session notes shown in prompt-20260508-080631-turn-3.txt (lines 60–63, 81–83, 97–100, 118–120) add phrases like "Evicted (relevance decayed to 0.53)" before each re-admitted fragment. A model reading this gets a relevance score datum but no actionable context. Per B9, recursive nesting of prior notes in new notes is also accumulating, which will compound this problem over time.

**Recommended action:** Either suppress eviction-only consolidation notes from context injection (they are noise), or upgrade `MechanicalConsolidation` to extract a meaningful sentence about the fragment's content before the eviction score. The `LlmConsolidation` path exists but is not the default — SCOPE.md's open item about making it default is directly relevant here.

## 7. dynamic.rs (39 chunks) dominates retrieval across unrelated queries

**Evidence:** `crates/caw-orchestrator/src/dynamic.rs` appears in the retrieved stubs for all three sessions across multiple turns, including queries where it is not the most relevant source. A comment in `caw-ingest/src/lib.rs` chunk 13/13 — retrieved multiple times across all sessions — explicitly says: "stale architecture text that outranks primary sources like". The file has 39 chunks, making it statistically likely to match any retrieval query by sheer coverage.

**Consequence:** dynamic.rs consumes retrieval slots that could serve more targeted stubs. In conjunction with B1's truncation behavior, dynamic.rs content also produces the most repeated noise strings in prompts.

**Recommended action:** Investigate whether dynamic.rs's stub summaries are too broad/generic. The comment in caw-ingest's lib.rs suggests this is a known problem. Per-file retrieval de-duplication (one chunk per source) exists in `DynamicRecallOrchestrator`, but the stale-architecture-text issue suggests the summaries themselves are attracting recall when they shouldn't.

## 8. Session turn-1 of session 080106 used search-candidates-only mode (0 workspace tokens)

**Evidence:** `prompt-20260508-080106-turn-1.txt` shows `─── PROMPT (0 workspace tokens across 0 fragments)` with only search-candidate metadata for "what is opencaw and why should I use it?" The model received stub outlines but not content. The model's response was reasonable but relied on the candidate metadata, not verified content.

**This connects to B4** (search-candidates mode fails silently when the model cannot request file loads). The model was told to "mention the specific files you need if you want them loaded" but the QA harness has no mechanism to fulfill that request. The model composed an answer from outlines alone, which for turn 1 happened to be accurate enough — but for a turn asking about implementation details it would hallucinate.

**Recommended action:** Either remove the search-candidates instruction from contexts where the QA loop cannot honor file-load requests, or implement file-load fulfillment in the QA loop (even a simple "if the model names a file in its response, load that stub for the next turn" heuristic).

## 9. Model's self-evaluation (session 080106 turn 2) accurately identifies context quality problems

**Evidence:** The model's response to "the context you see was generated by opencaw — is it helpful?" correctly identified: (a) redundant repeated chunks, (b) metadata noise from `Chunk X/Y` prefixes, (c) lack of hierarchical summarization, (d) query-type-agnostic retrieval dumping both high-level docs and low-level code snippets together.

**Why this matters:** These are all real, verifiable problems in the prompt files. The model's diagnostic is accurate because it's observing actual context. This is a useful test pattern — "evaluate your own context" — that could be added to the QA workload to provide a systematic signal about context quality from the model's perspective.

---

## 10. Answer quality is accurate when context matches the query; failures are retrieval failures, not reasoning failures

**Evidence:** When the right stubs were present, the model answered correctly. Session 080106 turn 1 produced an accurate architecture overview from README + SCOPE stubs. Session 080400 turn 2 accurately summarized the project status from codebase-review-report.md + SCOPE.md + BUGS.md. Session 080631 turn 3 correctly reported that caw-curation context was missing.

**Conclusion:** The model's reasoning is sound. The failure modes in this session are: history flooding the budget (observation 1), retrieval picking the wrong chunk within a document (observation 4), and retrieval missing an entire crate because the name wasn't matched (observation 2). Fixing retrieval quality will directly improve answer quality — there is no evidence of the model ignoring correct context when it's present.
