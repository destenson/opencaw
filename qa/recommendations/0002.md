## 1. Embed text is stub metadata, not chunk content — retrieval signal is almost entirely structural

**Severity: critical**

`SemanticRetriever::insert` embeds `"{path} {summary} {outline.join(" ")}"` — structured metadata only. The actual chunk content (code body) is passed as the second element of the `(Stub, String)` pair from `IngestionPipeline::ingest` but is **ignored** in `SemanticRetriever::insert` (the `_content: String` parameter is discarded, `caw-index/src/lib.rs:175`).

The consequence: embeddings encode symbol names and file paths, not code behavior. A query like "how does session eviction decide what to drop?" will not match the relevant `degradation.rs` chunks by meaning — it can only match by symbol name overlap (e.g. if "eviction" appears in a function name). Intent-based retrieval fails silently and is replaced by symbol-name lookup.

Compare `SemanticRetriever::insert` (metadata-only embed) with `HybridRetriever::insert` which passes the full content to BM25 (`bm25_text = format!("{} {} {}", stub.path, stub.summary, content)`). The semantic and BM25 retrievers are inconsistent in what text they index, compounding the problem for the hybrid path.

**Fix:** pass the chunk content body as the embed text (the chunk overlap+body that `IngestionPipeline` already computes), using the summary+path as a prefix for asymmetric models that expect it, not as the sole input.

## 2. DeterministicSummarizer produces structurally accurate but semantically empty summaries

**Severity: high**

Every stub in the index uses `DeterministicSummarizer` (the default in `IngestionPipeline::new`, `caw-ingest/src/lib.rs:83`). The `LlmSummarizer` exists but is never wired in at index-build time for this run.

For code chunks with outline entries, the summary is the position descriptor: `"Chunk 3/34 of ./crates/caw-orchestrator/src/dynamic.rs: contains impl Default for DynamicRecallConfig, fn default() -> Self"`. This lists symbol names but says nothing about what those symbols do. For chunks at the tail of a file (no outline entries — the last chunk of `caw-core/src/lib.rs` has summary `"Chunk 42/42 of ./crates/caw-core/src/lib.rs — /// so none of these methods are reachable at runtime."`), the summary is literally the last code comment in the chunk, which is random.

When the model sees a stub in "stub" range mode it gets `stub_descriptor(summary, outline)` — this is the stub's entire representation before it decides whether to probe for full content. If that representation is `"Chunk 42/42 … — /// so none of these methods are reachable at runtime."` the model has no idea what this chunk is about and will skip it even when it's relevant.

**Fix:** either enable `LlmSummarizer` for indexing (or for a post-index enrichment pass), or improve `DeterministicSummarizer` to use the outline entries as a fallback summary rather than the raw last line of content. The current tail-chunk path in `summarize_plaintext` uses the first non-empty line of the chunk body, which for code is often a closing brace or a mid-function comment.

## 3. Outline entries duplicated in both summary and embed text, biasing embeddings toward symbol matching

**Severity: high**

For code chunks with outline entries, the embed text (even under the current flawed metadata-only approach) is:
```
{path}  Chunk X/Y of {path}: contains fn_a, fn_b  fn_a fn_b fn_c fn_d
```

The outline symbols appear twice — once in the `position_summary` string that becomes the stub's `summary` field, and once in the `outline.join(" ")` appended during embed construction. This double-counts symbol names in the embedding, making them disproportionately influential compared to the path or any semantic content.

The decision point is `caw-ingest/src/lib.rs:155`: when `!chunk.outline_entries.is_empty()`, `position_summary` (which already contains the symbol list) is used as the entire summary, and then `caw-index/src/lib.rs:89` appends `stub.outline.join(" ")` again. The outline entries carried in `stub.outline` and those embedded in the summary text are identical.

**Fix:** when the summary already encodes outline entries (the code chunk case), skip the `outline.join(" ")` append in embed construction, or restructure so the summary contains semantic description and the outline contains symbols, not both containing symbols.

## 4. Extreme file fragmentation breaks file-level retrieval

**Severity: high**

`caw-core/src/lib.rs` → 42 chunks. `caw-orchestrator/src/dynamic.rs` → 34 chunks. `caw-orchestrator/tests/end_to_end.rs` → 7 chunks.

Each chunk is a ~400-token window with no information about the surrounding file context. A query about `DynamicRecallOrchestrator` (the central type in `dynamic.rs`) could match any of 34 separate stubs, each covering a narrow slice. The top-k slots get consumed by fragments of one file, crowding out other relevant files entirely.

There is also no mechanism to boost a file-level result (where the whole file is one stub) relative to a fragment-level result. A 50-token Cargo.toml stub and a 42nd-chunk tail of a 3000-line file compete on equal footing.

This is partly a chunking parameter issue (400 token chunks targeting 512-token BGE models is tight) and partly a missing file-level stub. For large files the system should either produce both a file-level summary stub and per-chunk content stubs, or use a larger chunk size to reduce fragmentation.

## 5. Zero consolidation notes despite session activity

**Severity: high**

The `consolidation_notes` table has 0 rows. Two session files are indexed: `.caw/session-20260508-040606.md` (7 chunks) and `.caw/session-20260508-040848.md` (4 chunks), confirming sessions were run. Yet no consolidation notes were produced.

This means the eviction-triggered consolidation path — the core novelty of the system — either never triggered (eviction threshold not reached in these sessions), triggered but the `MechanicalConsolidation` synthesizer produced notes that were not persisted, or the `with_consolidation_synthesizer` builder method was never called on `DynamicRecallOrchestrator` in the CLI setup.

Without consolidation notes, cross-turn memory is entirely absent. Retrieved stubs from early in a session carry no "this was relevant to the user's question about X" signal into later retrieval.

**Action:** add a diagnostic log when eviction occurs (or explicitly fails to produce a consolidation note), and verify that the CLI wires `with_consolidation_synthesizer` before running sessions.

## 6. Session files indexed, creating a retrieval feedback loop

**Severity: medium**

Session output files from `.caw/session-*.md` appear in the index (11 stubs). These contain Q&A turn transcripts produced by opencaw itself. Indexing them means retrieval can surface prior-session conversation artifacts as "relevant context" for new queries, which is a feedback loop: the system's outputs become inputs to future retrieval.

The `should_skip` function in `caw-ingest/src/lib.rs:391` explicitly excludes paths with a component starting with `.caw`. That filter was either absent when this DB was built, or the index was built with `skip_gitignore=true` which sets `hidden(!skip_gitignore)` to `hidden(false)`, allowing the walk to descend into hidden directories before `should_skip` fires. Since `should_skip` checks path components, it should still catch `.caw/` — investigate whether the walk is being invoked with different parameters in the bench build path vs. the CLI path.

## 7. Tail chunks produce misleading summaries from random code lines

**Severity: medium**

When a chunk has no outline entries (common for the last chunk of a file, which often contains test code, closing braces, or impl method bodies mid-way through a large impl block), the summary falls through to `summarize_plaintext`, which returns the first non-empty line of the chunk body.

Observed example: `"Chunk 42/42 of ./crates/caw-core/src/lib.rs — /// so none of these methods are reachable at runtime."` — this comment comes from a `#[cfg(test)]` block and describes a test invariant, not the module. The stub for this chunk looks like it's about unreachable runtime methods when it's actually the test module.

Similarly: `"Chunk 16/19 of ./crates/caw-bench/src/bin/build_index.rs — &mut done_files,"` — a mid-expression code fragment as the summary.

For chunks whose outline is empty, the summary should indicate the file and chunk position only, or try harder to find the nearest enclosing function/struct name from preceding outline entries.

## 8. Config and build files indexed with no useful retrieval signal

**Severity: low**

`Cargo.toml` files are detected as `PlainText` (`caw-ingest/src/lib.rs:381`) and indexed. Their summaries are first-line fragments like `"[workspace]"` or `"tracing = \"0.1\""`. A developer querying "what crates are in the workspace" would not reliably retrieve the root `Cargo.toml` because its summary contains no workspace membership information.

TOML/YAML config files could benefit from a dedicated outline extractor that pulls section headers and key names as outline entries, or be explicitly excluded from the index since they're navigable by path and offer poor embedding signal.

## 9. codebase-review-report.md and TODO.md consume disproportionate retrieval slots

**Severity: low**

`codebase-review-report.md` is chunked into 13 stubs, `TODO.md` into 10. These project management documents occupy the same retrieval pool as source code. For any query about system behavior, these chunks will compete (and with BM25, may win) over the code that actually implements the behavior.

These files should either be excluded via `.cawignore` or given lower retrieval priority via a per-kind score penalty.

## 10. Outline for code chunks contains raw multi-line signatures, breaking keyword matching

**Severity: low**

Tree-sitter-extracted outlines include full function signatures with embedded newlines (e.g., `"pub fn new(\n        retriever: R,\n        embedder: E,\n..."` in the DB). When `outline.join(" ")` is used in embed construction, newlines become spaces and the signature reads as one long token string. BM25 tokenization splits on whitespace, so `"pub"`, `"fn"`, `"new"` are indexed separately, which is fine for keyword search. But for embedding, a signature like `"fn synthesize_eviction_note(\n_fragment_content: &str,\nquery_context: &str,"` encodes a very different vector than the equivalent one-liner, causing inconsistency across chunks from the same file where some outline entries are one-line and some are multi-line.

The outline extraction in `tree_sitter_outline.rs` should normalize signatures to single-line form before storing them.
