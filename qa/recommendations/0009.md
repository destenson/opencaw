# QA Loop 0009 — Recommendations

Sessions analyzed: `session-20260508-065745.md` (2 turns), `session-20260508-065934.md` (3 turns, 18 prompt files), `session-20260508-070430.md` (3 turns, 17 prompt files). Model: `Qwen3.6-35B-A3B-UD-Q2_K_XL`.

---

## 1. Prior session model responses are retrieved as current context, creating response loops (critical)

At turn 3 of session 065934 ("how many todos are left?"), 5 of the first injected fragments are session history from session 065745 — the session that ran ~1.5 minutes earlier on the same topic. These fragments contain the prior session's full model responses (418 tokens about "context clutter," 448 tokens about "Filter Out Low-Value Artifacts," 222 tokens of formatting examples). In total, ~2500 tokens of the 6273-token context are prior-session model output.

The mechanism: `collect_previous_stubs` loads prior session logs into the in-memory HNSW index alongside workspace stubs. When session 065934 asks the same conceptual questions as 065745, the prior session's responses score as high or higher than actual workspace content, because they contain the same terminology in polished prose form.

Consequences: the model is effectively answering from its own prior output rather than from the workspace. The prior answer may be accurate, but the dynamic is that the retrieval system is rewarding verbose model responses as if they were authoritative documentation. If a prior response contained an error, the error propagates. This is the same propagation path documented in B3's notes but via in-memory rather than persisted stubs.

**Recommendation:** Session history fragments loaded from prior sessions should be summarized before indexing — surface the user queries and a short synthesis of the model's conclusions, not the full model response text. A prior session that generated a 400-token response about formatting should contribute ~50 tokens to the next session's context, not 400.

## 2. Session log truncation still active — QA observability covers only 3 of 18 turns (critical)

Both sessions 065934 and 070430 have 17-18 prompt files but only 3 turns in the session `.md` file (B2). All quality analysis for turns 4-18 is blind. The model's behavior on longer sessions, its handling of topic drift, and any accumulation effects are unobservable.

This makes QA loop 0009 almost useless for evaluating retrieval quality after turn 3: whatever is happening in the remaining ~80% of each session is invisible.

---

## 3. Inventory queries cannot be answered accurately — multi-chunk document coverage missing

"How many todos are left?" retrieved only Chunk 13/16 of `TODO.md`. The model correctly acknowledged it could only see one item from one chunk, but gave no reliable count. The session classifier has an `is_inventory_request` field that should influence retrieval strategy but apparently does not change chunk coverage. With 16 chunks of TODO.md at ~450 tokens each, loading all 16 would require ~7200 tokens; the current budget can't fit the full document.

The real problem is that there's no document-level retrieval path. When the user asks "how many X?", the system needs either: (a) a document-structure index that can answer "TODO.md has N open items" without loading all chunks, or (b) an outline-first pass that loads only the structural header of each chunk before deciding which chunks to expand.

**Recommendation:** For `is_inventory_request=true`, add a retrieval pass that fetches a document's outline/structural summary rather than its content chunks. TODO.md and BUGS.md stubs should have a canonical "index" stub (outline only, all sections visible) that gets boosted for count/status queries.

---

## 4. Cargo.toml stubs inject `[package]` into context despite summary filter claiming them fixed

The 0009 index contains 11 Cargo.toml stubs with `summary = "[package]"` and `token_estimate` values of 50–337. At injection time, the actual content shown is `[package]` (3 real tokens). The minimum-content filter (TODO item, marked done) filters on `token_estimate`, which reflects the full file size — not the summary content length. These stubs pass the filter (token_estimate > 10) but contribute zero signal.

Prompt evidence: `[fragment: ./crates/caw-core/Cargo.toml | 3 tokens] [package]` appears in turn 3 of session 065934.

**Recommendation:** The minimum-content filter should check summary content length, not token_estimate. Stubs where `len(summary.trim()) < 15` (or similar) should be excluded from retrieval regardless of file size.

---

## 5. Eviction notes accumulate mechanically without synthesis, growing fragment cost

By turn 3 of session 065934, `caw-orchestrator/src/probe_recall.rs` has 3 prior eviction notes attached, consuming 286+ tokens for entries that just say: "Evicted (relevance decayed to 0.5X) during query about '…'." The consolidation_notes table in the 0009 index contains only these mechanical eviction records — no synthesized insights. MechanicalConsolidation is the default; LlmConsolidation was not used.

Each time the stub re-enters context, it brings all prior eviction notes with it. By the third eviction cycle, the notes section is larger than the stub's original content for many small stubs. The notes don't help the model understand the stub better — they just document that the stub keeps getting dropped.

**Recommendation:** Cap eviction notes at N entries (e.g., 2). After N evictions, collapse repeated evictions into a single "Evicted N times, most recently relevance=X" summary. Consider whether mechanical consolidation notes add any value for the model at all vs. just counting evictions silently.

## 6. BUGS.md later chunks never retrieved — B3 through B6 invisible to the model

All three sessions consistently retrieved only BUGS.md Chunk 1/5, which covers B0, B1, and B2. Chunks 2–5 contain B3 (session log skip filter), B4 (search-candidates silent failure), B5 (hallucinated context), and B6 (fake recall markers). For queries asking about current status or known bugs, the model only reports the oldest three bugs.

This is both a retrieval gap and a signal about how BM25 and semantic search handle multi-chunk documents. The first chunk of BUGS.md has the highest density of "bug" and "critical" terminology, pulling it to the top while later chunks score lower despite being equally relevant to bug-status queries.

**Recommendation:** For key project documents (BUGS.md, TODO.md, SCOPE.md), add a document-level summary stub that enumerates all section headings and their status. When retrieved, this single stub lets the model know what exists before deciding which details to fetch.

## 7. Off-topic stubs persist in every session context regardless of query

MASCOT.md (mascot design criteria), `examples/ollama_demo.rs` (a `println!` statement), `crates/caw-llama-sys/src/lib.rs` (`#![allow(`), and `crates/caw-curation/src/history.rs` (LLM prompt string content) appear in every session's context across all 3 sessions of this loop. They are evicted each turn, then re-retrieved the next turn. None of these fragments have any bearing on the queries asked.

These stubs score high because they contain terms that appear in every OpenCAW-adjacent query ("context," "model," "recall," "session"). They are high-frequency-term noise attractors. The repeated eviction-and-reload cycle wastes both retrieval slots and budget scheduler decisions.

**Recommendation:** Track "eviction count since last positive engagement" per stub. After N consecutive evictions with no annotation or probe match, suppress the stub's retrieval score by a penalty factor. Stubs that keep getting loaded and immediately evicted are not useful for any query in this session.

---

## 8. Model responses are accurate and well-hedged where context is sufficient

Where the retrieved context directly covers the query (e.g., "what is opencaw?", "what can it do?"), the model's answers are grounded, accurate, and cite specific crate names and function signatures from the injected stubs. The model correctly admits uncertainty when it only has partial document coverage — noting "Chunk 13/16, implying there are likely more items." No fabricated recall markers were observed in 0009, suggesting the B6 strip_markers fix is working.

This is the expected baseline behavior; the issues above are about what context gets injected, not how the model uses it.

---

## 9. QA question set covers no retrieval-specific use cases

All three sessions in 0009 open with the same two conceptual questions ("what can you do with opencaw?", "is development completed?"). These are answered adequately from README.md and SCOPE.md alone, regardless of retrieval quality. No session tested: asking about a specific function's signature, tracing how a specific bug manifests, finding where a config option is set, or asking a question that requires synthesizing two files that aren't obviously co-related.

Questions of the form "what does `DynamicRecallOrchestrator::reset_session` do?" or "what's the relationship between GreedyBudgetScheduler and RecallThresholds?" would stress the retrieval system in ways that expose real gaps. The current question set is too high-level to surface retrieval failures that matter.

---

## 10. Token accounting mismatch: scheduler estimates vs actual injected content

The scheduler uses `token_estimate` from the stubs table to make budget decisions, but the actual injected content (summary + outline) can be significantly smaller. `caw-core/Cargo.toml` is estimated at 72 tokens but injects 3. This means the scheduler may be leaving budget on the table by over-counting small stubs, or under-counting fragments where the outline is large. The "5008 workspace tokens across 26 fragments" header is presumably the actual injected token count, but if the budget scheduler used estimated counts, its decisions may not reflect reality.

**Recommendation:** Measure and log the discrepancy between scheduled token estimate and actual injected token count per session. If the two numbers diverge significantly, the scheduler's budget enforcement is unreliable.
