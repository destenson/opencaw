## 1. B19 persists — valid prose answers flagged as degenerate on nearly every turn (critical, regression)

Every answer-phase turn in sessions 1 and 2, and three of four in session 3, terminated with `Error: degenerate output`. The flagged text is coherent, correct English prose — not Rust code (B00), not blank (B17), not looping repetition. The samples in the error messages confirm the model was on track:

- `"Based on the provided context, OpenCAW (Context as Workspace) is a framework that treats the AI model's context window a…"` (session 1, turn 2)
- `"Based on the recalled context, OpenCAW development is **not** completed. The project is in the **v1 development phase**,…"` (sessions 2 and 3, turn 2)
- `"Based on the recalled context, I can see that \`./TODO.md\` has 32 chunks in total. The system recalls specific items [rec…"` (session 2, turn 6)

All three are accurate, grounded answers. Only one turn in all of session 0020 completed without the degenerate flag: session 3 turn 6 (the initial completion for "what can we do to improve on the caw-curation crate?"), which produced a rich, evidence-grounded response.

The B16 fix (store the 120-char sample as the session answer) means sessions record partial truncated answers rather than blanks, which is better, but the answers are unusable — they cut off mid-sentence after a few words.

**Action**: Diagnose what pattern `is_looping` is matching in these valid responses. Add logging that emits the triggering pattern name (trigram collapse, line repetition, word dominance) and the approximate position in the text where it fires. If the trigger is a false positive (e.g., the phrase "Based on the recalled context" repeating across the context window rather than in the generation), adjust the window or the threshold. This single bug is responsible for almost all of 0020's failure.

## 2. Multi-pass refinement overwrites a good initial answer with a worse one (critical, bug)

Session 3, question 3 ("what can we do to improve on the caw-curation crate?") produced a good initial answer in turn 6 (8 fragments, 993 tokens): the model recalled code from `caw-core/src/lib.rs`, `caw-orchestrator/src/thinking_trace.rs`, and `context-as-workspace.md` and synthesized coherent improvement suggestions. That answer was never stored.

The refinement loop then ran turn 7 (11 fragments, 889 tokens — including `caw-curation/src/pipeline.rs`, `Cargo.toml`, and `lib.rs`). The model's response to the same question with more relevant context was: *"Based on the recalled context, there is no specific information available regarding a crate named `caw-curation`."* — a factually incorrect answer despite the curation stubs being present in context.

The system then ran turn 8 (50 fragments, 4574 tokens) which was flagged degenerate and stopped. The session log recorded the wrong answer from turn 7, not the better answer from turn 6.

Two sub-problems here: (a) the refinement loop discards the prior answer if a later pass completes without degenerate, even if the later answer is worse; (b) the model completely ignored `CurationResult`, `CurationPipeline`, and `CurationPipelineBuilder` from `pipeline.rs#chunk0` that were explicitly present in turn 7's context.

**Action**: Track a "best answer" across refinement iterations — keep the most recent non-empty non-degenerate answer from each iteration, not just the last one. Separately investigate why the model denied caw-curation exists when pipeline.rs was in its context (see finding 3).

## 3. Model ignores present caw-curation stubs and denies the crate exists (high, critical deficiency)

Session 3, turn 7 context included:
- `[caw-curation] [package]` (Cargo.toml)
- `[caw-curation] mod history;` (lib.rs)
- `[caw-curation] Chunk 1/5 of pipeline.rs: contains pub struct CurationResult, pub struct CurationPipeline<'a>, pub struct CurationPipelineBuilder<'a>`

Despite these fragments being in the prompt, the model replied that no information was available for `caw-curation` and asked the user to check if it's "perhaps a module within `caw-orchestrator` or `caw-core`". The stubs are minimal (`[package]` and `mod history;` are nearly empty), but `pipeline.rs` chunk 1 unambiguously names the crate and its types.

Likely cause: the minimal stubs (`[package]` alone, `mod history;` alone) were not enough to activate grounding in the model's answer. The model may have anchored on the outline-only fragments from `caw-core` and `caw-orchestrator` which had richer content, and dismissed the curation stubs as too sparse to confirm the crate exists.

**Action**: When the query explicitly names a crate, retrieval should preferentially load the most content-rich stub for that crate (not just the highest cosine-similarity chunk). `pipeline.rs` chunk 1 has a useful outline; `Cargo.toml` and `lib.rs` alone convey almost nothing. Consider a query-time crate-name match that boosts full-content chunks for explicitly named crates over stub-only chunks.

## 4. Session history carries truncated mid-sentence degenerate prefixes into subsequent sessions (high, bug)

The B16 fix stores the first ~120 chars of a degenerate response as the session answer. Session 1, turn 2 was flagged degenerate; the stored answer was: `"As an AI assistant operating within the OpenCAW framework, I can evaluate the context window you are currently seeing (w"`.

This truncated mid-sentence fragment was then injected as the prior assistant response in sessions 2 and 3, appearing in their history fragments as:

```
[Assistant]: As an AI assistant operating within the OpenCAW framework, I can evaluate the context window you are currently seeing (w
```

A mid-sentence truncation is actively misleading context — it implies the model was interrupted, suggests the topic is self-evaluation, and takes 95 tokens that add no signal. It also contaminated the history for every subsequent turn in sessions 2 and 3.

The root issue: B16 saves the sample text to the session log for human debugging purposes, but the session-history injection path uses that same log text as the model's prior answer. These two purposes need different treatment: the log entry should record the degenerate sample, but the text injected as history context should be omitted (or replaced with a brief `[turn skipped — model failed to produce a valid response]` placeholder).

**Action**: In `write_turn` (or wherever session history is recorded), mark turns where the answer came from the degenerate sample separately from turns with genuine answers. In `collect_previous_stubs` / the history injection path, skip or replace degenerate-sample turns with a one-line placeholder rather than injecting them verbatim.

## 5. Classifier fires degenerate for the query "is opencaw development completed? what's next to work on?" in both sessions 2 and 3 (high, bug)

The classification turn for that query failed with `Error: degenerate output from Qwen3.6-35B-A3B-UD-Q2_K_XL: …` in both sessions 2 and 3. Session 2 still produced an answer for the subsequent question (turn 4 also degenerate but session continued), suggesting the system has a fallback. However, the fallback classification is unclear — the subsequent answer prompt for that turn (turn 4 in session 2) included a `search-candidates` fragment suggesting is_next_step_request was active, which means the fallback must have defaulted to something.

This query is well-formed and similar to others that classified correctly ("is benchmarking finished?", "how many items remain?"). The classifier trigger may be query length or the two-question compound format ("is X? what's Y?").

**Action**: Log the fallback classification used when the classifier fires degenerate. Determine whether the classifier is being given the same system prompt as the answer model (and why the answer model degenerates too) or whether they share a temperature setting that is too high for deterministic JSON output. The classifier should be running at temperature 0 — verify this.

## 6. Session 1 terminates after 2 of 3 expected questions; 3rd "question" is "nice to know" (medium, bug)

Session 094900 has 5 prompt files. Turns 1-4 cover 2 QA questions (each with a classifier and an answer pass). Turn 5 is a classifier for `"nice to know"` which resolves to all-false flags and 0 fragments. This phrase is an acknowledgment, not a question — it should not be fed as input to the session.

Either the QA harness script sent "nice to know" as the third question (a defect in the question list), or the session encountered an error after 2 questions and tried to recover with user-like input. The session log records only 2 turns.

**Action**: Check the QA question list used for session 094900. If "nice to know" is literally in the question list, remove it. If it appeared due to a harness error (e.g., reading stdin after the piped input exhausted), add an assertion that each fed question matches a minimal length / contains a `?` or known question keyword.

## 7. TODO.md chunk 28/32 retrieved for virtually every query regardless of topic (medium, deficiency)

Across all 9 answer-phase turns in 0020, chunk 28/32 of TODO.md appears in the loaded fragments every single time — even for "what is opencaw and why should I use it?" (an explanation query) and "how many todos are left?" (an inventory query that needs chunk 3/32, the actual list). Chunk 28 contains the TODO item `"Include assistant answer in session history fragments, not just user query"` — a narrow implementation note that happens to use several high-frequency terms ("session", "opencaw", "context", "retrieved").

This confirms the observation from QA 0009 that a document-level index stub for TODO.md (headings + completion state only) is needed, and that high-frequency-term chunks from TODO.md will outcompete more relevant chunks when query terms overlap with the chunk content rather than the document intent.

**Action**: Implement the document-level overview stub for TODO.md (tracked in the existing TODO under "Add document-level overview stubs for key project docs"). Until then, consider a retrieval diversity penalty that reduces the score of a second chunk from the same document when a chunk from that document is already loaded.

## 8. Consolidation notes contain only eviction events, no synthesis (low, observation)

All 10 consolidation notes retrieved from `index.db` are of type `eviction`: `"Evicted (relevance decayed to 0.47/0.49) during query about '...'..."`. No LLM-generated synthesis notes appear. LLM consolidation was either disabled for this run or the synthesis path did not fire. The eviction notes themselves are valid and non-recursive (no nested nesting observed, suggesting B9 may be resolved or simply didn't trigger here).

**Action**: Confirm whether `--llm-consolidation` was passed in qa.sh for this run. If not, this is expected. If it was, investigate why no synthesis notes were generated — the model producing degenerate output on nearly every answer turn would also suppress stub annotation, which would suppress synthesis note generation.
