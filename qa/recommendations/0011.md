# QA Loop 0011 — Recommendations

Sessions analyzed: `session-20260508-074414.md` (2 turns, 10 prompt files), `session-20260508-074559.md` (3 turns, 11 prompt files), `session-20260508-074837.md` (3 turns, 10 prompt files). Model: `Qwen3.6-35B-A3B-UD-Q2_K_XL`. Sessions ran within 4 minutes of each other and covered overlapping questions: "what is opencaw", "what can you do with opencaw", "is development completed", "how many todos are left", "what can we do to improve caw-curation".

---

## 1. Blank response for inventory query — model reasoning succeeds, answer is empty (critical)

Session-074559 turn 3 ("how many todo's are left?") produced a 580-line thinking trace followed by a blank final answer in the session log. The model correctly identified the problem in its thinking: it had access only to chunk 16/22 of TODO.md and explicitly reasoned that it could not count todos from a single middle-of-file chunk. It worked out that the retrieved chunk described the B7 fix in narrative form, not a parseable item list, and that the prior session's model response had claimed 5 areas of improvement without supporting evidence.

After all that sound reasoning the model produced nothing. The session file records an empty response for that turn.

This is a new failure mode relative to 0009 and 0010. Prior sessions produced at least a hedged partial answer ("I can only see the B7 fix from the recalled evidence"). Here the model's thorough reasoning led it to produce no output at all. From the user's perspective the system silently failed.

**Recommendation:** Ensure the model always produces a visible response even when it identifies an information gap. The system prompt should instruct the model that when evidence is insufficient, it should explicitly say so with a concrete description of what's missing and offer to load more. A blank response is never correct.

## 2. Multi-pass recall explodes to 31 fragments / 5085 tokens for a simple count query (critical)

For "how many todos are left?", the initial workspace contained 22 fragments at 3734 tokens (already excessive). After one round of multi-pass recall, it grew to 31 fragments at 5085 tokens. The 9 new fragments included `thinking_trace.rs`, `session.rs` (4 chunks), `eval/metrics.rs`, `probe_recall.rs`, `bench/runner.rs`, and `bench/workload.rs`. None of these are relevant to counting TODO items.

The convergence detection recommended in 0010 has not been implemented. The loop is still running until budget exhaustion rather than stopping when marginal new-fragment value is zero.

At 5085 tokens, the prompt for "how many todos" is larger than the prompt for "what can you do with opencaw" (3197 tokens, turn-3 of the same session), even though the latter is a broader question that genuinely benefits from multiple retrieved stubs.

**Recommendation:** Implement convergence detection: stop the multi-pass loop if no new unique stubs were admitted in the last iteration, or if added tokens fell below a threshold (200 tokens suggested). This is already tracked in TODO as open from 0010 recommendation 2.

## 3. The correct TODO.md chunk is never retrieved for inventory queries (high)

When the intent classifier correctly sets `is_inventory_request=true`, the search-candidates list for "how many todos" contains `Chunk 3/22` of TODO.md (not chunk 1), plus `caw-index/src/embeddings/ort_setup.rs`, `caw-ingest/src/lib.rs::should_skip`, and `caw-orchestrator/src/dynamic.rs`. The loaded workspace gets chunk 16/22 of TODO.md, which describes the B7 fix narrative — not a list of open items.

Chunk 1 of TODO.md, which contains the section headers and the first items, was not retrieved in any of the 31 fragment loads across turns 9–11. An inventory query that can't see the document's top-level structure cannot produce a count.

This is the same failure documented in 0009 and 0010. The document-level overview stub for TODO.md has not been implemented. The `is_inventory_request` flag has no effect on retrieval strategy.

**Recommendation:** Implement the document-level overview stubs for TODO.md, BUGS.md, and SCOPE.md (already in TODO). When `is_inventory_request=true` or `is_status_request=true`, unconditionally include the first chunk of any file the intent classifier would prioritize, bypassing the similarity threshold.

## 4. Session history carries the verbatim prior model response at 1414 tokens — B7 persists (high)

In both session-074559 (turns 2 and 3) and session-074837 (turn 3), the "session history" fragment is 1414 tokens of the model's prior response to "is it helpful? is it too cluttered?". That single fragment accounts for 38–43% of the initial workspace budget before any workspace stubs are loaded.

The 1414-token history fragment is the model's own elaborate description of opencaw's architecture and improvement areas. Because it references every relevant concept (stub, recall, orchestrator, session, threshold), it scores as a top semantic match for nearly every subsequent query. For "how many todos are left?" — a fundamentally different question — this prior architectural explanation crowds out TODO.md content.

The recommended fix (≤50 tokens per prior turn through compact synthesis) from 0009 and 0010 has not been implemented. The B7 footprint is unchanged.

**Recommendation:** Before indexing a prior session response into the in-memory retrieval pool, replace it with a 1–3 sentence synthesis: what was asked, the main conclusion, and any specific facts cited. The synthesis replaces the full response in the embedding and as the injected text. Target ≤50 tokens.

## 5. Garbled fragment content under multi-pass: partial code and interleaved signatures (high)

Prompt turn-10 for session-074559 contains clear evidence of malformed fragment composition. At lines 1363–1364 in the prompt file, a `DynamicRecallOrchestrator::run_turn` function signature contains an injected field `cooperation_mode: CooperationMode,` that does not belong there — it appears mid-signature. At lines 1583–1644, the docstring phase descriptions repeat verbatim three times across different fragments from `dynamic.rs`, suggesting the same content window is being re-injected from different starting offsets.

There are also line-truncation artifacts: `[recalled from ./cr` (incomplete source path) appears at lines 1531 and 1573. These are cut-off fragment markers, meaning the fragment boundary was applied inside a `[recalled from ...]` header.

This is a variant of B1 (multi-pass recall corrupts fragment source paths). It appears under a different condition: heavy multi-pass with many fragments from the same large file (`dynamic.rs` has 38 chunks and multiple chunks appear in one prompt).

**Recommendation:** When the same source file contributes more than N chunks to a single workspace, deduplicate by taking the highest-scoring non-overlapping windows rather than all matching chunks. Already partially addressed by stub-ID deduplication, but window overlap from different-chunk-ID but overlapping-offset slices is not covered.

## 6. Consolidation notes accumulate recursively — nested eviction records grow unboundedly (medium)

In prompt turn-10, `probe_recall.rs` has a consolidation note that itself contains a nested consolidation note. The outer note reads "Evicted (relevance decayed to 0.51) during query about '...'. Source: ./crates/caw-orchestrator/src/probe_recall.rs. Topic: Chunk 1/5... [Prior session notes for this source: - Evicted (relevance decayed to 0.51) during query about '...' [Prior session notes for this source: ...]]". The recursion has at least 2 levels and the inner note text repeats the outer format verbatim.

This means the note for a stub is being composed by including the previous note text as part of the new note's "Topic" field. Each eviction appends the prior note's content as context. With enough eviction cycles, the consolidation header for a frequently-evicted stub will be larger than its content.

The cap on eviction notes (0010 recommendation 5) has not been implemented.

**Recommendation:** Cap consolidation notes at 2 entries per stub. When appending a new eviction note, strip any embedded prior-note content from the topic field — store only the summary text, not the prior note in its entirety. The note format should be: source path, chunk label, and one line of topic text. No recursion.

## 7. MASCOT.md retrieved for every "what is opencaw" query — noise stub still not suppressed (low)

MASCOT.md appears in session-074414 turn 2 (full recall, 140 tokens) and in session-074837's workspace. It contains mascot design criteria and marketing copy, contributing no information about the system's behavior or architecture. Both session 074414 and 074837 loaded it for queries that had nothing to do with branding.

This was noted in 0009 recommendation 7 and 0010 recommendation 7. It has not been addressed.

**Recommendation:** Add MASCOT.md to the skip list in `should_skip`, or add it to the corpus but exclude it from retrieval by marking its stub with a `no_retrieve` flag. Alternatively, tag it with a content type that is filtered unless queries contain branding-specific terms.

## 8. Search-candidates mode accurately serves explanation queries with 0 workspace tokens (positive)

Session-074414 turn 1 ("what is opencaw and why should I use it?") returned 0 workspace tokens in search-candidates mode. The model answered accurately from stub metadata alone, correctly naming all crates, their roles, the hybrid retrieval strategy, and the evaluation framework. No full content was loaded yet the answer was complete and accurate.

This confirms the 0009/0010 finding: for high-level architectural explanation queries, stub metadata is sufficient. The full-recall path adds noise for these query types.

The classifier correctly set `wants_explanation=true` and the system served search-candidates. This is the right behavior and it worked.

## 10. Three sessions in 4 minutes: B7 compounds within the same work window (observation)

Sessions 074414, 074559, and 074837 ran 1–4 minutes apart on overlapping questions. The 1414-token model response from session 074414 appeared as a session history fragment in both 074559 and 074837. By session 074837, the initial workspace for any non-trivial query would have contained this large prior-session response in addition to the current session's history.

This is the accumulation pattern noted in 0010 recommendation 9. Within a 30-minute window of repeated questions, B7 compounds: each session's verbose response becomes available to the next. The workspace for the third session in such a sequence carries the top-scoring responses from the prior two, which are all about the same topic with the same vocabulary.

**Recommendation:** Same as 0010 recommendation 9: TTL-based expiry or session-timestamp-based deprioritization for in-memory HNSW session embeddings. The fix for B7 (compact synthesis before indexing) from recommendation 4 above would also reduce this problem significantly by shrinking the injected response size from 1414 tokens to ≤50 tokens.
