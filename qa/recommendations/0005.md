# QA Loop 0005 — Recommendations

Generated from: `.caw0005/index.db`, three sessions (053256, 053439, 053702), 8–13 prompt files each.

Sessions ran three distinct QA questions:
- Session 053256: "you're using it right now; the context you see was generated by opencaw. Is it helpful? Is it too cluttered?"
- Session 053439: "is opencaw development completed? what's next to work on?" followed by "how many todo's are left?"
- Session 053702: same first question as 053439, followed by "what can we do to improve on the caw-curation crate?"

---

## 1. Session-log recycling: model copies prior session answers verbatim (B3 active)

**Severity: critical**

Session 053702 turn 1 answers "is opencaw development completed?" by recalling `session-20260508-053439.md` as its top-ranked fragment — a session log from a run minutes earlier that answered the same question. The model's thinking trace is explicit: it reads the prior session log and reproduces its answer. The two sessions' turn-1 responses are nearly identical, including bug numbers (B3, B4) and next-step wording.

This is B3 (`.caw/` skip filter broken) producing a measurable and concrete quality failure: answers to repeated questions are recycled from prior session logs rather than derived from primary sources (SCOPE.md, BUGS.md, TODO.md). If a prior session produced a hallucination or stale answer, it propagates forward with retrieval authority.

Prompt-053702-turn-4.txt confirms it: the first two fragments in the workspace are `session-20260508-053439.md` chunk 1/4 (61 tokens) and `session-20260508-053256.md` chunk 1/4 (50 tokens), ranked above SCOPE.md. These are recycled answers, not primary evidence.

B3 is the highest-priority open bug. Its fix is pre-condition for valid QA evaluation.

## 2. Multi-pass recall does not converge for status queries — workspace grows without bound

**Severity: critical**

Session 053439 prompt files show the same "is opencaw development completed?" turn progressing through iterations with fragment counts: turn-4 (23 frags, 1941 tokens) → turn-5 (46 frags, 3520 tokens) → turn-6 (42 frags, 2866 tokens). The workspace grew from 23 to 46 fragments across two thinking-trace iterations before settling. The core fragment set (SCOPE.md, caw-bench/README.md, dynamic.rs chunk 9, llama_cpp.rs chunk 14) remained constant across all three, with ~20 additional fragments added on each pass.

The retrieval is pulling in implementation files (llama_cpp.rs thinking-trace code, adapter_factory.rs, caw-adapters/src/lib.rs, caw-bench/src/main.rs) that contain no status information. These are low-precision hits: the semantic similarity to "opencaw development" finds code with variable names like `development_mode` or function signatures with "config" — but not status content. Precision falls as iterations increase.

This extends observation 8 from 0003 (8× token variance for the same query across sessions) and shows the variance is driven by multi-pass iteration, not just index randomness.

## 3. `scripts/qa.sh` indexed and surfaced as architectural documentation

**Severity: high**

`./scripts/qa.sh` chunk 6/7 appears in the top candidates for every query in every session — status queries, architecture queries, metacommentary queries. The chunk contains a CODEBASE LAYOUT section and QA prompt templates that describe the project structure in imperative terms ("YOUR TASK: 1. Read...", "cargo build --release --bin caw-cli"). The retrieval engine treats this as authoritative project documentation because it mentions every crate by name.

This consumes a retrieval slot in every query (37 tokens each) and injects misleading context: the CODEBASE LAYOUT list in qa.sh does not match the actual crate set (it omits caw-bench, caw-eval, caw-server, uses outdated names like "caw-workspace"). When the model answers architecture questions, it may source from this stale description rather than README.md or SCOPE.md.

The fix is to exclude `scripts/` from retrieval indexing, or at least exclude shell scripts that contain metacommentary about the project's own QA process. `.caw/` skip filter and scripts/ skip filter should be added together.

## 4. Metacommentary query ("is the context helpful?") retrieves deep implementation code, not architecture docs

**Severity: high**

Session 053256 turn 3 is the answer prompt for "you're using it right now; is the context helpful?" — a metacommentary question about opencaw's output quality. The injected context (prompt-053256-turn-3.txt) is enormous: full implementations from `caw-curation/src/pipeline.rs`, `caw-curation/src/tool_output.rs`, `caw-core/src/scheduler.rs`, `caw-adapters/src/llama_cpp.rs`, `caw-eval/src/session.rs`, and 30+ other fragments. Total: 1900+ lines of raw code.

The model receives this because multi-pass recall fires on a query about "context" — which matches any code that uses the word "context" in variable names or comments. The retrieval is searching for the concept "workspace context" but finding `context_budget_tokens`, `n_ctx`, `KV cache`, etc. as high-similarity hits.

The model's answer discusses the structure of the recalled context accurately (it correctly identifies `CurationPipeline`, `ToolOutputCompressor`, etc.) but is missing the architectural overview that would answer the intent of the question. It treats implementation details as evidence about system design.

For queries about opencaw's own context format, the correct sources are `context-as-workspace.md` and `README.md`. The search results surface these (chunk 1, 11 of context-as-workspace.md; chunk 1 of README.md) but they are buried in 30+ implementation files.

## 5. Intent classifier returns all-false for count and metacommentary queries, disabling intent-driven retrieval

**Severity: high**

"How many todo's are left?" classifies as all-false. "Is the context helpful?" classifies as all-false. Both should trigger intent-driven behavior: the first is clearly `is_inventory_request` or `is_status_request`; the second is novel but benefits from proactive loading of design documentation.

The result: session 053439 turn 2 ("how many todos?") gets a random retrieval hit that returns only one chunk of TODO.md showing a single completed item. The model correctly hedges ("I can only confirm at least one todo was completed") — but this is a retrieval failure. The full TODO.md has 25+ items across many chunks. Without intent-driven full-document loading (observation 3 from 0003), count queries fail by design.

The intent classifier covers `is_inventory_request`, `is_status_request`, `is_next_step_request`, `is_results_request`, `wants_latest_run_only`. "How many X are left?" maps cleanly to `is_status_request` + `is_inventory_request`. The classifier is undertriggering these flags. The training/prompting for the classifier needs examples with count language ("how many", "how much", "total", "remaining").

## 6. Search-candidates mode surfaced to answer model without load mechanism — still broken (B4 carry-forward)

**Severity: high**

Session 053256 prompt turn-2 is a classifier call; turn-3 is the answer prompt. The answer prompt correctly receives a search-candidates list (11 files, 507 tokens) rather than raw content. The candidate list includes the right files: context-as-workspace.md chunks 11 and 17, README.md chunk 1, SCOPE.md. But the model is instructed "Mention the specific files you need if you want them loaded" with no mechanism to honor that request.

The model's answer (visible in session-053256.md) is grounded entirely in the content it can infer from the stub summaries — it's describing the system architecturally but not quoting from specific code. This is an improvement over loading wrong code, but the model is working from discovery metadata rather than evidence.

The fundamental problem (B4) persists: search-candidates is a dialog protocol stub that requires a tool-call loop to be useful. In a one-shot QA harness, it delivers worse grounding than just loading top-k candidates directly. The answer shows the model hallucinating minor details ("The use of `Outline:` fields in `caw-curation`") that aren't present in the stub list it received.

## 8. Fragment summaries for code-only chunks are code lines, not semantic descriptions

**Severity: medium**

The index DB shows several stub summaries that are raw code lines rather than semantic descriptions. Examples:
- `Chunk 4/4 of ./crates/caw-bench/src/opencaw.rs — | ".git"` — the summary is a literal code line from a `.git` filter in a path exclusion list
- `Chunk 6/12 of ./crates/caw-bench/src/main.rs — // tempdir backs SqliteStubStore...` — a comment from mid-function

When these appear in search-candidates lists, they give the model no useful signal about what the chunk contains. The model cannot decide whether to load `caw-bench/src/opencaw.rs chunk 4/4` based on `| ".git"`. This also means BM25 and semantic retrieval index on the wrong signal — these stubs rank on incidental code content rather than the module's semantic purpose.

This is a summarization failure for short trailing chunks: the last few chunks of a large file often contain closing braces, test modules, or boilerplate, and the LLM summarizer (or the fallback deterministic summarizer) generates a summary from whatever text is available rather than defaulting to a parent-level description.

## 9. Session log truncation confirmed in all three sessions (B2 carry-forward)

**Severity: medium**

- Session 053256: 8 prompt files, 1 turn in session log
- Session 053439: 13 prompt files, 2 turns in session log
- Session 053702: 13 prompt files, 2 turns in session log

The pattern is consistent: roughly 1 turn visible per 6–7 prompt files, suggesting the session log writer flushes or exits after the second or third user turn. The rest of the session output is unrecorded. QA analysis using session markdown files misses most of each session's behavior.

This was flagged in 0003 and is still active. The fix (flush after every turn, not only on exit) is in TODO.md but remains unimplemented.
