## 1. Session log recycling leads to fabricated caw-curation recommendations (B3 still active)

**Severity: critical**

Session 055659 started at 05:56:59. Session 055445 ended at approximately 05:54:45. Session 055328 ended even earlier. In session 055659 turn 5 prompt, the top fragments are `.caw/session-20260508-055445.md` (chunk 1/2, 37 tokens) and `.caw/session-20260508-055328.md` (chunk 2/5, 101 tokens) — both recycled session logs from the same QA run.

The model's answer to "what can we do to improve on the caw-curation crate?" explicitly cites session-20260508-055328.md as its source: *"From the session notes (`session-20260508-055328.md`), there is a focus on improving how the system handles clutter and large chunks. Specifically: Implement Dynamic Relevance Scoring & Pruning. Implement Enhanced Summarization for Large Chunks."*

Those "recommendations" are the model's own improvised answers from the metacommentary session — they are not in caw-curation's TODO list, SCOPE.md, or any design document. The model is being asked for curation improvement ideas and is receiving its own prior hallucinations as authoritative source material.

This is a concrete, reproducible propagation path: model improvises in session A → session A's log gets indexed → model in session B retrieves session A's log → session A's improvisation becomes session B's grounded recommendation. B3's partial fix (updating `build_index.rs::should_skip`) is not sufficient because the CLI inserts active session logs into the live HNSW index via `SessionFile::load_previous`.

The fix requires the live-session insertion path to use an in-memory-only index that is not persisted to the SQLite store, so re-indexing on next run does not include them.

## 2. Fragment boundary collapse produces truncated garbage strings in multi-pass context

**Severity: critical**

Prompt file `prompt-20260508-055444-turn-3.txt` (the multi-pass answer turn for "is opencaw development completed?") is 2094 lines long and contains hundreds of entries like:
```
[recalled from ./crates/c
[recalled from ./crates/caw-
[recalled from ./cr
[recalled from ./crates/caw-orch
[recasured from ./crates/caw-
```

These are truncated path strings where fragment boundary detection split mid-`[recalled from ...]` tag. They appear interleaved with legitimate content. The effect:
1. These garbage lines consume context tokens without conveying information.
2. They indicate the same source file is being recalled dozens of times in a single prompt (B1 symptom: multi-pass re-admits the same file repeatedly).
3. The rendered context becomes unreadable at scale — the model is receiving a corrupted input for a straightforward status query.

This is B1 (multi-pass recall corrupts fragment source paths) still active. The token count for this turn reaches 3840 tokens across 50 fragments before the session stabilizes, partly because of duplicate admits.

## 3. Status queries load implementation code instead of status documents

**Severity: high**

The 23-fragment initial workspace for "is opencaw development completed?" (prompt-055444-turn-4) contains:
- `./crates/caw-adapters/src/groq.rs` (211 tokens — struct definitions and constructors)
- `./crates/caw-adapters/src/anthropic.rs` (188 tokens — same)
- `./crates/caw-orchestrator/src/thinking_trace.rs` (235 tokens — config struct)
- `./crates/caw-orchestrator/src/probe_recall.rs` (176 tokens — struct definitions)
- `./crates/caw-eval/src/session.rs` (135 tokens — method signatures)
- 4× `[package]` Cargo.toml fragments (3 tokens each, no content)
- 1 fragment of groq_demo.rs containing only `thresholds: RecallThresholds::default_hysteresis()`

What the query actually needs: `SCOPE.md`, `BUGS.md`, `TODO.md`, and `codebase-review-report.md`. Of these, only `codebase-review-report.md` chunk 1/13 (57 tokens) was retrieved, showing only the executive summary opening line. SCOPE.md appeared in session 055659 but not 055444.

The semantic retrieval matches "opencaw development completed" against any fragment containing the word "development" in variable names or function comments — pulling in implementation files that happen to use `development_mode`, `default`, or `config` as identifiers. There is no signal from this retrieval set that answers whether the project is done.

The model handles this correctly — it reports "not completed, here is what the code structure suggests" — but it is reasoning from the wrong evidence. Its conclusion is directionally correct but unsupported, and it misses the definitive sources (TODO.md, SCOPE.md).

## 4. Count queries remain unanswerable — "how many todos?" returns 1 of 14 chunks

**Severity: high**

Session 055444 turn 2 ("how many todo's are left?") receives only `./TODO.md` chunk 12/14 in the workspace — a single completed item (`[x] Skip retrieval...`). The model correctly hedges: "it is not possible to determine the exact number of remaining TODOs." This is the same failure mode documented in QA 0003 and 0005.

The index contains all 14 chunks of TODO.md with useful summaries (`Chunk 1/14: contains TODO, Retrieval, Ingestion & Indexing`, etc.). The problem is that semantic search on "how many todos are left" returns the chunk with the most textual overlap to the query's vocabulary, which happens to be a chunk containing the word "todo" densely in list-item text.

The intent-driven augmentation signals fix (`is_inventory_request` → load all TODO.md chunks) is in TODO.md as an open item but unimplemented. Without it, every count or tally query against a fragmented document is systematically unanswerable.

## 5. Consolidation notes still zero after four consecutive QA loops

**Severity: high**

`SELECT COUNT(*) FROM consolidation_notes` on `.caw0008/index.db` returns 0. Same result in 0002, 0003, 0005. Four loops, zero notes.

Sessions 055444 and 055659 both ran 13 prompt turns each. The workspace reached 50 fragments with 3840 tokens at peak. Either:
- The `DynamicRecallOrchestrator` is not being constructed `with_store()` in the QA harness, so consolidation notes go only to in-memory provenance and are never written to the SQLite store.
- Eviction never fires because the workspace stays below the 80% eviction threshold.
- The persistence path is silently broken.

Until diagnostic logging lands (open TODO item), the QA loop cannot distinguish these cases. Four loops of zero-notes means the consolidation feature has received zero integration testing in any real session. This is a gap regardless of the root cause.

## 6. Model treats prior session output as architecture documentation

**Severity: high**

In session 055659, when answering "what can we do to improve on the caw-curation crate?", the model's step 3 explicitly recommends *"Address Known Bugs in Curation Flow — Refer to `./BUGS.md`... B3: `.caw/` session log skip filter not working at index build time (medium): This suggests issues with how curation or ingestion handles existing session logs."*

B3 is not a curation bug. It is an ingestion/indexing bug. The model is misattributing B3 to the curation pipeline because the session logs it retrieved contain references to B3 alongside discussion of curation — and it cannot distinguish "a prior session's analysis of bugs" from "the actual BUGS.md file."

Separately, the model invents a concrete file path: *"specifically in the `CurationPipeline` defined in `./crates/caw-curation/src/pipeline.rs`"* — this path is correct, but the model deduced it from the session log's naming style rather than from having `pipeline.rs` in its workspace. This is the model pattern-matching on prior session output to sound grounded.

## 7. Multi-pass recall does not converge and builds up to 50 fragments for a 2-turn session

**Severity: medium**

Session 055444's prompt files show fragment counts growing across recall passes for the single query "is opencaw development completed?":
- turn-3 (search-candidates, 0 frags loaded): 587 tokens
- turn-4 (initial recall): 23 fragments, 1810 tokens
- turn-5 (second pass): 50 fragments, 3840 tokens
- turn-7 (third pass): 33 fragments, 2264 tokens

The drop from 50 to 33 between turn-5 and turn-7 indicates eviction fired at some point (or this is the next user turn's first pass). But reaching 50 fragments on a "is it done?" question indicates the convergence criterion is not working: each thinking-trace step is finding new files to load because every Rust file in the codebase contains some tokens that match "opencaw", "development", "status", or "config".

The orchestrator's `loaded_sources` deduplication (one chunk per source file) should cap growth, but the workspace at 50 fragments means ~50 different source files were admitted. For a status query, this is retrieval without selectivity.
