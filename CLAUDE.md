# Project Goal

**OpenCAW (Context as Workspace)** is a Rust library that treats the model's context window as a managed workspace instead of a fixed buffer that must hold everything up front. Documents are indexed as lightweight stubs; full content is loaded, evicted, and consolidated inline as the model reasons, so only the content relevant to the current step stays resident while the rest of the corpus remains available on recall. The goal is to keep context free of tokens that are not relevant to the current reasoning, which is what lets the effective context cover a corpus much larger than the window at roughly flat compute cost.

The mechanism for deciding what to load, evict, and consolidate is the model's own reasoning trace, rather than a retrieval step that runs once before inference. This trace-driven loop is the part that distinguishes OpenCAW from generic RAG. The library is general-purpose; project-specific heuristics do not belong in it.

See `docs/origin.md` for the founding design (the settled premise, not a proposal under evaluation) and `docs/scope.md` for what is in and out of scope for v0.1.

For **current priority, sequence, and what to work on next** — the question "where should we go next?" — read `docs/ROADMAP.md`. It carries the ordered critical path to the next milestone and the forcing logic behind that order, which `TODO.md` (unordered backlog), `BUGS.md` (open defects), and `docs/DECISIONS.md` (settled choices) deliberately do not.

- **USE RELEASE BUILDS FOR BENCHMARKING** Always use release builds (e.g. `cargo build --release`) when benchmarking or profiling the codebase to get accurate performance measurements. Debug builds include additional checks and instrumentation that can significantly impact performance, so they should not be used for benchmarking. Using release builds ensures that you are measuring the performance of the optimized code that will be used in production, rather than the slower debug version.
- **During development, use the caw-dev skill** Use the `caw-dev` skill for building, running, testing, and benchmarking the OpenCAW stack during development. This skill includes scripts that encode best practices for interacting with the codebase, such as GPU pinning, batch-size workarounds, and release-build flags. By using the `caw-dev` skill's scripts instead of hand-assembling commands, you can ensure that you are following the recommended patterns for working with the codebase and avoid common pitfalls. If the skill does not have a script for a particular task, consider adding one to the `docs/skills/caw-dev/scripts/` directory for future use.
- **Option<T> struct members** When adding members to existing structs, consider whether the new field should be optional (e.g. `Option<T>`) to preserve backward compatibility with existing serialized data. If the field is required, adding it will break deserialization of old data that lacks the field. If the field is optional, new code can handle missing values gracefully while still supporting old data.
- **Default implementation** When adding members to existing structs, consider whether the struct should have a Default implementation that provides reasonable defaults for the new fields. This can help ensure that existing code that constructs the struct without specifying the new fields continues to work without modification. If the new fields are optional, the Default implementation can set them to None or some other default value.
- Prefer to construct new structs with { field: value, ..Default::default() } syntax to ensure that any new fields added in the future will be properly initialized with their default values, rather than risking uninitialized fields if the struct is later extended with new required fields.
- **Source of truth for design decisions** `docs/DECISIONS.md` is the authoritative reference for settled implementation choices: feature defaults, skip lists, retrieval budgets, session history caps, consolidation behavior, intent classifier wiring, convergence criteria. When encountering any ambiguity about how something should be implemented, read `docs/DECISIONS.md` before making a choice. When `docs/DECISIONS.md` is silent, see its Decision Protocol section — the correct response is usually to present options with trade-offs rather than to pick one.
- **Features must be on by default** Every feature must be active without a flag. Opt-out flags are acceptable for A/B testing (e.g., `--no-consolidation`). Opt-in flags are not acceptable — if a feature is in `docs/DECISIONS.md` or `docs/scope.md`, it is on by default.
- **Recommendations for improving the codebase found by QA** Recommendations for improving the codebase may be found in qa/recommendations/*.md.
- **NEVER HARDCODE RESPONSES** Do not hardcode any expected responses from the model in the implementation code. The implementation should be robust to changes in the model's output format or phrasing. If specific response formats are required, they should be clearly documented and tested against, but the implementation should not rely on exact string matches that could break if the model's output changes slightly.
- **Never short circuit the model** Do not short circuit the model by hardcoding expected outputs or bypassing the model's reasoning process. The implementation should always allow the model to generate its response based on the provided context and prompt, rather than forcing it into a specific answer. This ensures that the system remains flexible and can adapt to changes in the model's behavior or output format without breaking.
- **Do not put project-specific heuristics in the codebase** This codebase is intended to be a general-purpose library for retrieval-augmented generation (RAG) applications with context curation. Avoid hardcoding any heuristics, thresholds, paths, or logic that are specific to the OpenCAW project or its particular use cases. Instead, design the library to be configurable and extensible so that users can implement their own heuristics or logic on top of the core functionality without modifying the library's internal code.
- It's not helpful to output "[degenerate]" or similar messages in the implementation code when the model generates an unexpected response. Instead, the implementation should handle such cases gracefully, by retrying and logging a warning and continuing to the next query rather than aborting the entire session. This allows for more robust handling of edge cases without hardcoding specific responses or behaviors that could break if the model's output changes. Furthermore, this is not production code, this is still under development, so hiding details from the user (THE DEVELOPER) is not at all helpful. The implementation should provide as much information as possible about what went wrong to aid in debugging and development.
- Don't strip bad output, detect it & mitigate it. This project is still under development, do not hide data from the developer.
- Prefer to use error!(...) logging with detailed information about what went wrong, rather than short-circuiting the model or hardcoding expected responses. This allows for more robust handling of edge cases and provides valuable information for debugging and improving the system without relying on brittle string matches or assumptions about the model's output.
- Prefer to use info!(...) logging to provide insights into the system's behavior and decisions, rather than relying on hardcoded responses or short-circuiting the model. This allows for better transparency and understanding of how the system is functioning, which is especially important during development and debugging.
- Prefer to use warning!(...) logging to highlight potential issues or unexpected behavior in the system, rather than hardcoding expected responses or short-circuiting the model. This allows for more robust handling of edge cases and provides valuable information for debugging and improving the system without relying on brittle string matches or assumptions about the model's output.
- **Use the logging system for errors, warnings, and informational messages** Instead of printing directly to the console or using eprintln!, use the logging system (e.g. error!(...), warning!(...), info!(...)) to log messages. This allows for better control over the output, such as setting log levels, formatting, and directing logs to files or other outputs. It also provides a consistent way to handle messages across the codebase and can be easily adjusted as the project evolves without changing the underlying implementation logic.
- Don't create bugs in BUGS.md you just fixed. Only log a bug if it is still present in the codebase. If you have already fixed a bug, there is no need to log it as an error or warning, as this can create confusion and clutter the logs with information about issues that have already been resolved. Instead, focus on logging any remaining bugs or issues that are still present in the codebase to provide clear and actionable information for further development and debugging.

While improving infrastructure can be valuable, it should be done in a separate branch and PR focused on infrastructure improvements, rather than being mixed into bug fixes or feature development. This helps keep the focus of each change clear and makes it easier to track the impact of specific changes on the system's behavior and performance.

## Principles

- Code should be re-used as much as possible. In particular, `caw-cli`, `caw-bench`, and the tests/QA/dev harness should all use the same underlying library code for retrieval, indexing, and evaluation to ensure consistency and reduce duplication. Move duplicated logic into `caw-core` or a new crate as needed, but avoid copy-pasting code between the CLI, bench, and harnesses.
- Context is the LLM's workspace, not a fixed window, not a data dump. Opencaw allows a model's context to be a curated workspace that changes dynamically over time, rather than a static window that must hold everything up front. The model's reasoning trace is the signal for what to load, evict, and consolidate, so the context stays focused on what the model currently needs while still allowing access to a much larger corpus through recall. This is the core principle that distinguishes OpenCAW from generic RAG approaches, and it should guide all design and implementation decisions.
