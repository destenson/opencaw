# Context as Workspace: On-Demand Recall and Curated Working Sets for LLMs

**Status:** design notes, pre-implementation
**Scope:** prompt transformation, embedding-driven recall, context curation policy

---

## 1. Scope and Deployment Model

This is a **general-purpose framework** for context management, not a specific application. The framework defines the core abstractions — stub generation, recall, curation policy, eviction — as a library. Deployment targets are implemented as adapters on top of the framework.

Planned deployment targets, roughly in order:

1. **Library** — embeddable in any application that constructs LLM prompts.
2. **Middleware/proxy** — sits between a client and a remote LLM API, transparently managing context.
3. **Engine plugins** — native integration with inference engines (vLLM, Ollama, etc.) for local users managing context in-situ. This is the long-term goal but depends on the framework stabilizing first.

### Non-goals

- Replacing true long-context for tasks that genuinely require simultaneous access to all material.
- Training or fine-tuning models to be aware of the recall substrate.
- Building a specific end-user application (the framework enables applications, it isn't one).

---

## 2. Thesis

LLM context is a *workspace*, not a *container*. Effective capability is set by working-set quality, not total accessible information. Treating context as a managed resource — with explicit policies for admission, retention, summarization, and recall — yields larger effective reach and better reasoning than naively expanding the window.

Two consequences drive the rest of this document:

1. **Context-extension via on-demand recall** can plausibly multiply effective context by 1–2 orders of magnitude on retrieval-shaped tasks, at roughly flat compute cost, by trading storage for attention.
2. **Context curation** — what *isn't* in the workspace at any moment — is itself a primary lever on output quality. Noise in context is dilutive, not neutral.

The two are complementary: recall makes the active set smaller without losing reach; curation makes the active set sharper.

## 3. The Stub-and-Recall Architecture

### 3.1 Prompt transformer

A preprocessor walks an input prompt, finds file references (markdown links, `@path`, fenced blocks with `path=`, bare paths matching a regex — pick the surface), and replaces each with a structured stub. The original span is preserved so content can be spliced back inline on demand.

Each stub carries enough metadata for the model to triage without reading:

- stable id (short handle: `f3`)
- path
- size + token estimate (using the *target model's* tokenizer, not char/4)
- mtime, content hash (for cache invalidation when mtime is unreliable)
- mime / detected kind
- short summary (1–3 sentences) — for prose, LLM-generated; for code, deterministic extraction (tree-sitter symbols) preferred over summarization
- outline (headings, symbol list, sheet names, etc.)

Stub format should parse reliably. Tagged blocks work:

```
<file id="f3" path="notes/spec.md" tokens=4200 mtime="2026-04-10" kind="markdown">
  summary: Design doc for cache eviction; covers LRU vs ARC tradeoffs and a hybrid proposal.
  outline: [Goals, Background, Proposal, Benchmarks, Open Questions]
</file>
```

**Stub generation timing: background indexer with lazy fallback.** A background process continuously generates stubs for workspace files (summaries, outlines, token counts). If a file is referenced in a prompt before the indexer reaches it, stub generation happens on demand for that file. This amortizes the preprocessing cost for stable workspaces while avoiding cold-start blocking on first request.

Summaries are cached on `(path, mtime, hash)` and generated by a cheap model, distinct from the consuming model.

**Index granularity is adaptive.** Small files (under a configurable token threshold) are indexed as a single unit. Large files are automatically chunked and each chunk indexed independently. No hierarchy — the system decides based on file size. This avoids the complexity of hierarchical matching while still enabling fine-grained recall for large files.

### 3.2 Recall mechanism

The model's own thinking is the retrieval query. With reasoning-trace models this is essentially free: thinking output is more topical and denoised than mixed user/assistant turns, and step boundaries provide natural trigger points.

#### Execution model: multi-turn orchestration with optional mid-stream optimization

The **baseline** execution model is multi-turn orchestration. Each "reasoning step" is a separate generation call. Between calls, the orchestrator inspects the output, runs the recall pipeline, and injects any recalled content into the next turn's prompt. This works with any LLM API — local or remote — since it only requires standard request/response semantics.

For inference engines that support it (e.g., vLLM plugin mode), an **optional mid-stream optimization** can interrupt token generation at step boundaries, inject content, and resume without restarting the full generation. This is architecturally cleaner but requires deep engine integration, so it's a second-phase optimization, not a prerequisite.

The orchestrator loop:

1. Send prompt to model.
2. Receive output (partial or complete).
3. At step boundaries: embed the reasoning step → top-k against stub index → for any hit above threshold not already loaded, splice content into context.
4. If content was injected, continue generation with the augmented context. If not, pass through.
5. Repeat until generation completes.

#### Two expansion paths: automatic probes and manual tools

These are **separate, coexisting mechanisms** serving different purposes.

**Automatic recall (probes):** For models with visible reasoning traces, embed the trace at step boundaries and match against the stub index. For models with hidden traces, instruct the model to emit short `<probe>...</probe>` markers when reasoning about something it only has a stub for. Either way, matches above threshold trigger automatic content injection. The model doesn't need to know this is happening — probes are a natural byproduct of reasoning.

**Manual recall (tools):** `read_file(id, range)` and `grep(id, pattern)` are explicit tool calls the model can invoke deliberately. These give the model precise control: partial reads, pattern searches, targeted expansion. Tools work with any model that supports tool use, regardless of whether automatic recall is active.

Both paths feed into the same content-injection and provenance-tagging machinery. A model might receive automatic recalls for broadly relevant files while using tools to drill into specific sections.

### 3.3 Why the embeddings-on-residual-stream version doesn't work zero-shot

Hooking activations and projecting them into the file-embedding space is the literal interpretation of "trigger loading from what the model is thinking about." It fails without training data because sentence-encoder space and LLM residual space aren't commensurable — a learned projection requires labeled (activation → correct file) pairs. Thinking-trace embeddings sidestep this entirely by matching in shared text-embedding space.

### 3.4 Engineering details that matter

- **Asymmetric embeddings.** Use a query/document encoder pair (e5, bge families). Thinking step is the query, file is the document.
- **Hysteresis.** Load at e.g. 0.7 cosine, unload at 0.4. Prevents thrashing near threshold. These are starting points — actual thresholds are workload-dependent and should be tuned via measurement (see section 10).
- **Suppress already-loaded files** from the candidate pool, so the model reasoning *about* a loaded file doesn't re-trigger.
- **Top-k with margin** when a step mentions multiple files; load all that clear threshold up to budget. k and margin are configuration parameters, not constants — reasonable defaults TBD through measurement.
- **Embed at step boundaries**, not per token. Punctuation + length heuristic for models without explicit step delimiters.
- **Insertion order of recalled content** is deferred to measurement. Candidates include relevance-ranked, reverse-relevance (most relevant closest to generation point), and original-stub order. This is an empirical question, not an architectural one.
- **Model awareness of the recall mechanism is capability-dependent.** Capable models benefit from knowing the mechanism exists — they can reason strategically about what to probe. Weaker models may over-probe or attempt to game the system. The framework should support both modes: cooperative (system prompt explains the mechanism) and transparent (mechanism is invisible to the model). Detection heuristics for which mode to use are a deployment-level concern.

## 4. Provenance and the False-Recall Problem

When content materializes inline between reasoning steps, it's indistinguishable from material the model had read earlier. From the model's side this feels like recall rather than retrieval, which is roughly the right abstraction but introduces a failure mode: if the stub summary is slightly wrong, or the embedding match fires on a spurious file, the model "remembers" something untrue of the source. Worse, it now holds both stub-derived prior and actual content, possibly conflicting, with no signal to reconcile them.

**Mitigation: precise inline provenance.** Every materialized fragment is tagged with locator:

- `[recalled from spec.md:4-12]` for code/text by line range
- `[recalled from spec.md#Benchmarks/Latency]` for prose by heading path
- `[recalled from results.xlsx!Sheet2:B4-D40]` for cells
- `[recalled from interview.txt @00:14:22-00:15:48]` for transcripts

Precision matters: the more locatable the material, the more the model treats it as quoted source rather than gist, and the better it can flag conflicts with prior expectation. Locators also let the model ask precise follow-ups (`expand spec.md:13-40`) instead of refetching whole files.

This breaks the seamlessness of recall slightly. That's the right tradeoff.

## 5. Eviction Policy

Eviction uses a **combined** strategy: a token budget as a hard ceiling, with relevance decay as the soft policy within that budget.

- **Token budget.** Recalled content has a configurable maximum token allocation (a fraction of the model's total context window, or an absolute cap). This is the hard constraint — the system never exceeds it regardless of relevance scores.
- **Relevance decay.** Each recalled fragment's relevance score decays over reasoning steps. The decay rate is configurable. When a fragment's score drops below the unload threshold (the 0.4 hysteresis floor), it becomes a candidate for eviction.
- **Eviction order.** When budget pressure exists (new recall wants space, or the budget is full), evict the lowest-relevance fragments first. Ties broken by recency (older evicts first).
- **Eviction is not deletion.** Evicted content returns to stub form. The stub may be enriched with consolidation notes (see below).

### Consolidation: hybrid model

When content is evicted, the stub absorbs a brief note of what was learned during the loaded period. Re-recall later is then informed by the prior visit. The stub becomes mutable and gets richer over time — closer to human episodic-to-semantic transfer than to caching.

The consolidation mechanism is **hybrid**:

1. **Mid-session annotations.** The consuming model emits brief annotations as it reasons about loaded content — lightweight markers noting what was relevant and what was concluded. These are cheap (a few tokens each) and capture the model's actual reasoning context.
2. **Eviction-time synthesis.** A separate, cheap model synthesizes the accumulated annotations into a coherent consolidation note and attaches it to the stub. This runs outside the active session's token budget.

This captures the accuracy advantage of mid-session generation (the consuming model knows what mattered) without paying the full cost of summary generation in the active context.

## 6. Degradation Modes

Components fail independently. The system degrades in tiers rather than failing atomically.

| Tier | Condition | Behavior |
|------|-----------|----------|
| **Full recall** | All systems healthy | Automatic probes + tool-based reads + eviction + consolidation |
| **Stubs + tools only** | Embedding service slow/down, or probe rate excessive | Files still replaced with stubs (saves context space). Automatic recall disabled. Model uses `read_file`/`grep` tools manually. |
| **Pass-through** | Summary cache cold for large workspace, or stub generation failing | Prompt passed through unmodified. No stubs, no recall. Model works with whatever fits in context natively. |

Each component monitors its own health:

- **Embedding service**: latency threshold + error rate. Degrades probe-based recall independently of tool availability.
- **Summary generator**: queue depth + error rate. If the background indexer is behind and lazy generation is failing, fall back to pass-through for unindexed files (indexed files continue working).
- **Probe rate limiter**: if the model emits probes at an excessive rate (suggesting thrashing or gaming), throttle automatic recall and fall back to tools-only for that session.

Degradation is per-component and can recover. If the embedding service comes back, automatic recall resumes on the next step boundary.

## 7. Limits of Effective-Context Extension

Honest ceilings:

- **Recall rate is workload-dependent.** Factoid lookup: high. "Find the lemma whose proof technique applies here": much lower — that's reasoning-shaped, not similarity-shaped. Hybrid retrieval (embedding + BM25 + structural) helps but doesn't close it.
- **Cross-file synthesis is the hard case.** Sequential reasoning across recalls works; simultaneous synthesis of fragments from many files breaks down when they don't all fit. Summarization-on-eviction mitigates but is lossy in exactly the cases where detail mattered.
- **Coherence across recalls is not free.** Long real context has implicit consistency from being processed by one pass. A backing store doesn't — two recalls in the same conversation can surface contradictions the model never sees adjacent. Needs explicit reconciliation prompts or a running ledger of "what I've recalled and concluded."
- **Preprocessing tax.** Summary generation costs LLM calls and must be regenerated on content change. Amortizes for static corpora; continuous cost for live filesystems.

Realistic estimate: 1–2 orders of magnitude effective-context expansion for retrieval-shaped tasks, less for synthesis-shaped, on roughly flat inference compute. This stacks with whatever the model's real window provides; it isn't a replacement for true long-context where genuine simultaneity is required.

The right comparison isn't "embedding-recall vs. 10M context" — it's "embedding-recall + 200k context vs. 10M context, on equal compute." First wins for most tasks; sharp flip for synthesis-heavy ones.

A secondary effect worth noting: reasoning quality probably *improves* with a smaller, more relevant active set up to some floor. So this is potentially a context-*quality* improvement that happens to also extend reach.

## 8. Curation: The Other Half

If the workspace framing is right, then everything in context competes for attention. The principles:

- **System prompts should be ruthlessly short.** Defensive clauses for the 1% case degrade the 99% case; degradations compound.
- **Conversation history is mostly debt.** Default chat-UI behavior (preserve everything until forced eviction) is the laziest possible policy.
- **Tool results are the worst offenders.** Verbose dumps blow tens of thousands of tokens on material relevant for ten seconds.
- **Few-shot examples have a sweet spot.** Two well-chosen examples often beat ten; more biases toward surface form and consumes workspace.
- **Reasoning competes with content for the same budget.** No current model exposes a separate scratch buffer. Asking a model to reason extensively about a large document is often worse than asking it to reason about a summary, even with information loss.

The reframing: stop asking *what should I tell the model* and start asking *what should the model be thinking about, and what's the least context that lets it think about exactly that.*

### 8.1 Curation policies

The framework defines **curation hooks** — extension points where concrete policies plug in. Each hook has a default policy that can be overridden per deployment.

#### History summarization

- **Trigger:** when conversation history exceeds a configurable token threshold (e.g., 30% of the context budget).
- **Policy:** summarize old turns into a compressed representation. Preserve: decisions made, facts established, current task state. Drop: exploratory reasoning that led to dead ends, verbose tool outputs from completed steps.
- **Default implementation:** a cheap model generates a running summary, updated every N turns. The summary replaces the turns it covers.
- **Retention exception:** the most recent K turns are always preserved verbatim (configurable; default 3). This ensures the model has immediate conversational context.

#### History externalization (alternative to summarization)

Rather than compressing history, it can be externalized to the filesystem and recalled on demand via the same stub-and-recall machinery used for workspace files — practically eliminating context-length restrictions on history without lossy compression.

- **Storage unit:** one file per session (not per turn). Session files are structured text the existing ingestion pipeline can handle; the adaptive chunker splits them at turn boundaries.
- **Write path:** the orchestrator appends each turn to the active session file and immediately indexes the new chunk. No file watching needed — the writer and the indexer are the same process.
- **Closed sessions:** treated as immutable documents. Re-indexed on hash change, which handles user redactions without special casing.
- **Recall:** probe/embedding matching surfaces relevant prior exchanges inline, tagged `[recalled from history/2026-04-30.md:turn-12]` so the model knows it is remembering, not reading a new source. The retrieval path is identical to file recall.
- **Tradeoff vs. summarization:** lossless, but retrieval-shaped — exchanges that were topically diffuse when written may not surface on a semantically focused query. The most recent K turns should still be kept verbatim in context as a retrieval floor.

#### Tool output compression

- **Trigger:** any tool result exceeding a configurable token threshold.
- **Policy:** tool outputs are stubbed using the same architecture as file stubs. The full output is stored in the backing index; the context receives a summary stub.
- **Default format:** `"[tool: grep] 234 files searched, 5 matched filter. Top matches: [list]. Full results available via recall."` The model can use `read_file` or probes to access full results if needed.
- **Exceptions:** tool outputs explicitly marked as "inline-required" by the deployment (e.g., short computation results, yes/no answers) bypass compression.

#### System prompt budgeting

- **Policy:** system prompts have a configurable maximum token budget. The framework measures system prompt token usage and warns (or truncates, depending on deployment config) when the budget is exceeded.
- **Guidance (not enforced):** system prompts should be under 10% of the total context budget. Deployments that exceed this should audit for defensive clauses, rarely-triggered instructions, and verbose formatting.

#### Few-shot management

- **Policy:** few-shot examples in the prompt are counted against the context budget like any other content. The framework provides a utility to measure the marginal token cost of each example.
- **No automatic policy.** Selecting and pruning few-shot examples is too task-specific to default. The framework surfaces the cost; the deployment decides.

### 8.2 Overflow strategies

When reasoning legitimately needs simultaneous access to more material than fits in context, three strategies are available. The orchestrator (or user) selects based on task type:

1. **Summary-of-summaries.** Recursive summarization until the material fits. Lossy but always produces a result. Best for: broad synthesis where gist is sufficient.
2. **Multi-pass with reconciliation.** Process subsets of the material sequentially, then a reconciliation pass merges findings. More faithful but slower. Best for: detailed analysis where precision matters.
3. **Surface the constraint.** Report to the model (and user) that the task exceeds simultaneous context capacity, with specifics on what doesn't fit. Let them decide how to decompose. Best for: interactive sessions where the user can guide decomposition.

The framework provides all three as primitives. Default behavior is to surface the constraint — the other strategies require explicit opt-in since they involve quality tradeoffs the user should be aware of.

### Worked example

**Setup:** A user asks a coding assistant to "refactor the auth module to use JWT instead of session tokens." The workspace contains 40 files. The model's context window is 128k tokens.

**Step 1 — Prompt transformation.** The prompt references `@src/auth/` implicitly via the task description. The transformer identifies 6 files in the auth module and replaces them with stubs:

```
<file id="f1" path="src/auth/middleware.rs" tokens=1800 mtime="2026-04-14" kind="rust">
  summary: Express-style auth middleware; validates session tokens against Redis store.
  outline: [SessionValidator, validate_request, refresh_session, RedisSessionStore]
</file>
<file id="f2" path="src/auth/types.rs" tokens=400 mtime="2026-04-12" kind="rust">
  summary: Auth type definitions: SessionToken, UserClaims, AuthError.
  outline: [SessionToken, UserClaims, AuthError, AuthResult]
</file>
...4 more stubs...
```

Total stub cost: ~600 tokens (vs. ~8,000 for the raw files).

**Step 2 — First generation.** The model begins reasoning: "To refactor from session tokens to JWT, I need to understand the current session validation flow. The middleware in f1 validates against Redis..."

**Step 3 — Probe fires.** The orchestrator embeds the reasoning step. It matches `f1` (middleware.rs) at 0.82 cosine and `f2` (types.rs) at 0.75. Both clear the 0.7 threshold. Their full content is spliced into context with provenance tags:

```
[recalled from src/auth/middleware.rs:1-62]
pub struct SessionValidator { ... }
...
```

**Step 4 — Continued generation.** The model now has the actual code and reasons about the specific changes needed. It uses `read_file(f4, "lines 30-45")` to check how the session store is initialized — a targeted tool call, not a full file load.

**Step 5 — Eviction.** After the model finishes with `f2` (types.rs) and moves on to implementation, f2's relevance decays below 0.4 over several steps. It's evicted. The model had annotated "UserClaims struct needs `exp` and `iat` fields for JWT; AuthError needs a `TokenExpired` variant." A cheap model synthesizes this into a consolidation note attached to f2's stub.

**Step 6 — Later re-recall.** When the model circles back to update type definitions, f2's stub now includes the consolidation note. The model (or a probe match) recalls f2 again, this time with prior context about what changes were planned.

## 10. Action Items

Roughly ordered by ratio of value to effort.

1. **Build the prompt transformer.** Stub generation, background indexer with lazy fallback, summary cache keyed on `(path, mtime, hash)`, target-tokenizer token counting, deterministic outline extraction for code (tree-sitter) and prose (heading parse), adaptive chunking for large files. Standalone, useful immediately even without recall.
2. **Build `read_file(id, range)` and `grep(id, pattern)` tools.** Range-addressable reads against the stub index. Manual expansion path; works with any model.
3. **Build the multi-turn orchestrator.** Step-boundary detection, context injection between turns, token budget tracking. This is the execution backbone for everything else.
4. **Add explicit-probe recall.** Instruct the model to emit `<probe>` markers; embed probes; auto-expand on threshold. Works with any model, doesn't depend on visible traces.
5. **Add thinking-trace recall** for models with visible CoT. Step-boundary embedding, hysteresis, top-k with margin, suppress-loaded-files filter. Same expansion machinery as (4).
6. **Add provenance tagging** to all materialized content. Format per content type (line range, heading path, cell range, timestamp).
7. **Add eviction with hybrid consolidation.** Token budget enforcement, relevance-decay tracking, mid-session annotations, eviction-time synthesis into mutable stubs.
8. **Add curation hooks.** History summarization, tool output compression, system prompt budgeting. Default policies per section 8.1.
9. **Add degradation monitoring.** Per-component health checks, tiered fallback per section 6, probe rate limiting.
10. **Instrument and measure.** Recall@k on a held-out workload, false-recall rate (provenance-tagged conflicts), effective vs. nominal context ratio, hysteresis threshold tuning, insertion-order experiments. Without measurement the architectural choices are guesses.

## 11. Remaining Open Questions

The following questions were raised during design and resolved:

- **Cooperative vs. inferred triggering** → capability-dependent (section 3.4).
- **Index granularity** → adaptive: small files whole, large files chunked (section 3.1).
- **Consolidation timing** → hybrid: mid-session annotations + eviction-time synthesis (section 5).
- **Overflow handling** → all three strategies as framework primitives (section 8.2).

Still open:

- Whether models, given this substrate, develop reasoning patterns that exploit it — deliberately thinking *around* a topic to surface related material, the way a person mutters to jog memory. If so, prompting strategy itself shifts. This is an empirical question that can only be answered after the system is running.
- The right heuristic for detecting model capability level (to choose cooperative vs. transparent mode). Proxy candidates: model family, benchmark scores, observed probe quality in a calibration phase.
- Whether the adaptive chunking threshold should be token-based, structural (e.g., chunk at function/section boundaries), or both.
- Cache invalidation strategy for live filesystems where mtime is unreliable and content changes frequently. The `(path, mtime, hash)` key handles correctness but not cost — frequent changes mean frequent re-summarization.
